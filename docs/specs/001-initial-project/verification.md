# Проверка реализации TempVoice

Дата: 2026-11-13. Среда: Windows x64, Node.js 24.22.1, npm 11.19.1. Реальный Discord, Docker и сервер развёртывания не использовались.

## Реализованное состояние

- Команды сборки, проверки типов и Vitest; ESM/NodeNext с decorator metadata. `start:dev` использует tsc-watch и запускает скомпилированный JavaScript.
- Отдельные Nest-контексты основного процесса и CLI. Настройки Discord, SQLite и health передаются через узкие неизменяемые Config. Ошибки конфигурации содержат имя настройки без значения.
- Конфигурация приведена к примеру GoldGiverBackend: env-группы в `src/config/env`, общая валидация class-transformer/class-validator, модульные Config с private readonly полями и getters, injectable ConfigFactory, FactoryInterface и CreateConfigProvider. Options TypeORM собирает DatabaseOptionsFactory через useClass и extraProviders.
- JSON-логгер и адаптер логирования TypeORM без SQL, параметров и сырых сторонних ошибок.
- Очередь по ключу и отдельный исполнитель коротких операций одного соединения SQLite. Повторный захват своей очереди завершается ошибкой вместо взаимного ожидания.
- Семь моделей у владельцев данных и две сгенерированные TypeORM миграции, включая отметку незавершённой очистки guild. Включены WAL и ожидание блокировки 1000 мс, `synchronize` выключен. Runtime и CLI используют общий состав моделей, миграций и options.
- Repository временных каналов: сохранение, чтение, подсчёт всех отслеживаемых каналов, условное резервирование попытки удаления и идемпотентное удаление записи. Попытка резервируется отдельной завершённой операцией до будущего Discord DELETE.
- Добавлены Repository и Service триггеров и лимитов, Handler регистрации, снятия наблюдения, изменения лимита, AFK и удаления триггера. DiscordVoiceChannelAdapter реализует VoiceChannelGatewayInterface; Observer подключён к Necord, основной процесс выполняет login и остаётся работать. Команды ещё отсутствуют; сеть в проверках подменяется.

## Проверки каркаса и схемы

Исторический результат до подключения Discord и добавления второй миграции. Актуальная проверка интеграции описана в последнем разделе.

| Проверка | Результат |
| --- | --- |
| `npm ci`, `npm ls --depth=0` | Установка и дерево зависимостей без обхода peer conflicts. Install script разрешён только для better-sqlite3 12.11.1; необязательный postinstall Necord отключён. |
| `npm run lint`, `npm run format:check`, `npm run typecheck`, `npm run build` | Успешно. |

| Миграция на новой SQLite и повторный запуск | Одна запись истории; повторное применение не меняет схему. TypeORM не обнаружил расхождений схемы с моделями. |
| Скомпилированный migration CLI без Discord token | Два запуска `migration:run` на временной БД успешны; после обоих история содержит одну миграцию. |

Установка сообщила о moderate advisory в дереве инструментов разработки. Принудительные обновления закреплённого стека не выполнялись.

## Проверка исправления конфигурации

После рефакторинга сохранены те же пять бизнес-тестов. Отдельных автоматических тестов getters, библиотечной валидации и DI wiring не добавлялось. Локальная smoke-проверка скомпилированного приложения подтвердила:

- дефолты SQLite и health совпадают с прежними, относительные пути нормализуются в env-слое;
- ConfigFactory получает уже проверенную свою env-группу, Config предоставляет прежние свойства через getters;
- ошибочные значения каждого из трёх runtime-параметров останавливают запуск с ненулевым exit code; ошибки содержат имя настройки и не раскрывают секрет-маркер, stdout остаётся JSON;
- основной процесс штатно создаёт и закрывает контекст; конфигурация проверяется до подключения к БД;
- `.env` загружается из рабочего каталога; запуск из отдельного временного каталога создаёт SQLite по заданному относительному пути, не раскрывая token в логах;
- CLI и два последовательных запуска миграций работают при отсутствующем token и некорректной неиспользуемой health-настройке;
- история содержит одну миграцию, TypeORM не находит расхождений схемы, WAL и timeout 1000 мс сохранены;
- старые EnvironmentConfigService, ConfigurationModule, три отдельных ConfigurationModule и функция CreateDatabaseOptions удалены вместе с зависевшими от них импортами.

Для этого подхода добавлены закреплённые runtime-зависимости class-transformer 0.5.1 и class-validator 0.15.1. После изменения lockfile повторно прошли `npm ci`, `npm ls --depth=0`, lint, format:check, typecheck, пять бизнес-тестов и build.

## Триггеры, лимиты и жизненный цикл временного канала

На этом этапе `npm test` выполняет **52 теста в пяти файлах**. Тесты бизнес-сценариев используют настоящую SQLite с миграцией и подменяют Discord-операции; чистые правила cooldown и идентичности входов проверяются без БД. Ранее написанные пять тестов бюджета удаления сохранены. Проверены:

- отказ для Stage, неподходящего типа, AFK, уже управляемого временного канала и недостаточных permissions из gateway-контракта;
- повторный watch без записи в SQLite и без переноса границы новых входов;
- индивидуальный лимит до watch, сохранение при unwatch/rewatch, снятие наблюдения при AFK, очистка только неактивной конфигурации без лимита и связанных каналов;
- удаление настройки физически удалённого триггера без удаления его временных каналов; проблемные каналы и каналы без триггера остаются в лимитах;
- одновременные входы в разные триггеры не обходят общий лимит; несколько входов в один триггер не обходят индивидуальный;
- значение 0 снимает ограничение, снижение лимита не удаляет существующие каналы и не создаёт новые до освобождения слотов;
- cooldown 5 секунд устанавливается после успешного перемещения, действует по guild/user, не затрагивает других пользователей и не возникает после отказа создания, ошибки перемещения или отката;
- приём перехода до очереди, граница успешного watch, исключение уже присутствующих пользователей и событий, полученных во время watch; одинаковый channel ID и боты не создают вход;
- выход и возврат в тот же триггер делают старый вход недействительным; повторная доставка обработанного входа не создаёт канал даже после истечения cooldown;
- ID канала сохраняется до перемещения; устаревший вход после Discord create вызывает общий откат, занятый канал сохраняется;
- попытка удаления фиксируется до внешнего DELETE, расходуется не более трёх попыток, немедленного retry-цикла нет; подтверждённое отсутствие очищает запись при любом бюджете;
- неизвестный состав и занятость не запускают удаление. После резервирования пустота проверяется повторно: если за время записи вошёл человек, DELETE не выполняется, но зарезервированная попытка остаётся потраченной;
- конкурентные запросы удаления и пересечение с откатом получают результат одной попытки; тест сначала воспроизвёл расход двух попыток, затем прошёл после исправления;
- отказ сохранения после Discord create не объявляется успехом: выполняется безопасная компенсация известного ID, ID остаётся в безопасном логе; необратимый отказ закрывает допуск новых и ожидающих guild-операций, временная SQLite busy не закрывает допуск;
- ожидание Discord в одном guild не блокирует другой guild и не удерживает очередь SQLite.

Отдельная локальная smoke-проверка собранного JavaScript создала настоящий Nest application context с `VoiceModule.withGateway` и подменённым модулем внешних операций. Через публичные Handler выполнены watch, установка лимита, создание, сохранение ID, перемещение, сохранение занятого канала и удаление после опустения. SQLite настоящая; после `app.close()` DataSource закрыт. Это проверка сборки и DI с подменой Discord, без login, Gateway или HTTP.

Repository остаются внутри своих функциональных модулей. Service/Handler получают DTO и числа, не ORM Entity/Repository. Новые env-параметры и зависимости на этом этапе не добавлялись.

## Ограничения и следующий этап

`main.ts` пока проверяет и закрывает каркас, а не запускает работающего Discord-бота. Бизнес-модуль Voice готов к подключению модуля с реализацией VoiceChannelGatewayToken, но реального Discord-адаптера ещё нет, поэтому App не подключает этот модуль. `console.ts` пока не выполняет `owner:recover` или health. Команды миграций уже доступны отдельно:

```powershell
npm.cmd run migration:run
npm.cmd run migration:generate -- src/modules/Infrastructure/Database/Migration/NextChange
```

Проверка путей в env-слое пока проверяет строковый формат и нормализует путь. Доступность файла SQLite проверяет фактическое открытие БД; создание и проверка health-файла относятся к T072.

Автоперезапуск `start:dev` и Linux-сборка нативного драйвера на этом этапе не проверялись.

T013 остаётся открытой до проверки очереди SQLite в Ownership/T052; создание и лимиты уже проверены. T022 выполнена частично: остались атомарные операции Ownership. Команды, recovery, health и deployment ещё отсутствуют; реальные Discord permissions и сетевой reconnect не проверены.

## Discord Gateway, сверка и завершение операций

Актуальный результат этапа: **72 теста в восьми файлах**. Новые тесты защищают собственные правила копирования канала, классификации состава и доступности, сверки и завершения операций. Настоящие SDK-объекты используются для enum, permissions и коллекций; внешние вызовы подменены.

- Один POST передаёт совместимые голосовые настройки, изменяемый флаг и permission overwrites, без позиции. Существующий overwrite создателя объединяется без дубликата; добавляются только ViewChannel, Connect и ManageChannels, соответствующие Deny снимаются, остальные права сохраняются. Unicode-имя не обрывает суррогатную пару. Невоспроизводимые overwrites отклоняются до POST.
- Пустота определяется по обычным пользователям, боты не учитываются. Неизвестный участник, потеря ViewChannel, обфускация и ошибка доступа оставляют состояние Unknown. UnknownChannel становится Missing только в прежнем доступном поколении. Голосовые состояния перечитываются после ожидающих обращений.
- Начальная сверка не создаёт комнаты для уже присутствующих пользователей. Новые входы сохраняются до окончания сверки; ушедший пользователь не получает комнату. Выход из уже проверенного канала во время сверки не теряется. Предыдущие поколения входов после reconnect недействительны.
- Занятые и недоступные временные каналы остаются в SQLite и лимитах; подтверждённо отсутствующие очищаются. AFK теряет регистрацию, сохраняя индивидуальный лимит; физически удалённый триггер теряет настройку, сохраняя связанные временные каналы.
- Подтверждённый channelDelete идемпотентен. Прерванная очистка guild сохраняет отметку и продолжается после повторного открытия настоящей SQLite; повторное приглашение guild также сначала завершает старую очистку. Временная недоступность не очищает данные.
- Необратимый отказ записи созданного ID компенсирует известный канал и уведомляет основной процесс о завершении. Shutdown отклоняет ожидающие и новые операции, ждёт выполняющуюся; превышение 15 секунд завершается ошибкой. Срок проверен с управляемыми часами Vitest.

Сквозная ручная проверка скомпилированного приложения использовала настоящий Nest application context, Necord listeners и SQLite, с подменой login и сетевых операций. До импорта приложения заданы фиктивный token и временные пути. Любой неожиданный REST request отклонялся. Подтверждено:

1. БД с первой миграцией и существующими каналами обновилась до двух миграций без потери данных до вызова Client.login; listeners уже зарегистрированы.
2. ClientReady запустил сверку без создания комнаты; VoiceStateUpdate прошёл через декоратор Necord до создания, сохранения ID и перемещения. Последующий выход удалил пустой канал; занятый сохранился.
3. GuildUnavailable сохранил SQLite, GuildAvailable выполнил сверку, GuildDelete запустил подтверждённую очистку.
4. Синтетическое уведомление channelDelete внутри REST-операции поставлено отдельной операцией. Обнаруженная при первой проверке ошибка наследования контекста очереди исправлена и защищена регрессионным тестом.
5. При app.close текущая операция удерживалась проверочным барьером: Client.destroy ещё не вызывался, DataSource оставался открытым. После снятия барьера завершились операция и закрытие обоих ресурсов.

После изменений выполнены `npm.cmd run lint`, `npm.cmd run format:check`, `npm.cmd run typecheck`, `npm.cmd test`, `npm.cmd run build` и проверка diff. Сверка схемы TypeORM не обнаружила расхождений моделей и миграций.

Это локальная проверка интеграции, а не проверка настоящего Gateway/API. Копирование полей и минимальные разрешения на тестовом guild, настоящий сетевой reconnect, команды, health/CLI health, Docker и серверная приёмка остаются впереди. Новые env-переменные на этом этапе не добавлялись.
