## 1. Стек и сборка

Базовая проверенная связка: Node.js 24.22.1, NestJS 12.5.0, Necord 7.1.1, discord.js 14.28.1, TypeORM 1.1.3, better-sqlite3 12.11.1, TypeScript 5.9.3 и Vitest 5.1.0. Операторский CLI использует nest-commander 3.21.0 с адресным override его nestjs-discovery на 7.1.0 для Nest 12. Полный список проверенных зависимостей и границы проверки находятся в research.md. Версии фиксируются в package.json и package-lock.json.

Приложение — ESM с `module` и `moduleResolution: NodeNext`, strict-проверкой типов, `experimentalDecorators` и `emitDecoratorMetadata`. Относительные импорты исходников используют расширение `.js`. Runtime-классы, необходимые для DI и метаданных, сохраняются в обычных импортах. Проверенный запуск использовал `skipLibCheck: false`.

Компиляция выполняется через `tsc`, запуск — из `dist`. `tsconfig.json` используется для анализа без эмита; при подготовке сборки `tsconfig.build.json` наследует его, включает эмит в `dist` и исключает тесты. В `dist` попадают основной процесс, CLI и миграции. Бизнес-тесты создают проверяемые классы с тестовыми зависимостями; выполнение тестов не требует компиляции Nest application context.

Реализованные npm scripts: `build`, `typecheck`, `check`, `lint`, `lint:fix`, `format`, `format:check`, `test`, `test:watch`, `start`, `start:dev`, `migration:generate`, `migration:run`, `migration:revert`, `owner:recover`. Локальная команда `npm run check` последовательно выполняет format (автоисправление ESLint и Prettier, затем проверка результата), typecheck и build, останавливаясь при первой ошибке. `npm run format` также доступна отдельно; lint и format:check сохраняются для проверок без изменений в CI. `start:dev` использует tsc-watch и запускает скомпилированный JavaScript с decorator metadata. `owner:recover` запускает готовую сборку; перед первым использованием или после изменения кода выполнить build. Команда `health` остаётся в T072.

Линтер — ESLint 10.14.0 с `@eslint/js` 10.0.1 и `typescript-eslint` 8.72.2. Анализ `@throws` сохраняется через `eslint-plugin-explicit-exceptions` 0.13.3; для его устаревшего peer range применяется адресный npm override на корневой ESLint. Код плагина и правила не изменяются. Сравнение ESLint 9 и 10 на 27 примерах подтвердило одинаковые сообщения и 12 автоисправлений. | `Core` | Общие технические компоненты, включая очередь выполнения по ключу. |

Triggers и Limits не импортируют Voice. Handler в Voice получает данные через их публичные Service и передаёт подготовленные факты соответствующему бизнес-правилу. Например, при watch сведения о том, является ли канал временным, получает Handler через VoiceService; TriggersService не обращается к чужому Repository.

Разделение DiscordGatewayModule и DiscordModule устраняет обратный импорт: Voice использует адаптеры первого, а транспортные обработчики второго используют Voice. Gateway-модуль не импортирует транспортные Controller, Handler и бизнес-сервисы. Контракты адаптеров принадлежат потребляющей функциональной области.

Handler входит в очередь операции один раз. Его внутренние вызовы Service и общих сценариев удаления не захватывают ту же очередь повторно. Правила создания, отката и сверки используют одну логику жизненного цикла Voice.

## 3. Конфигурация и точки входа

Главный процесс получает проверенные `DISCORD_TOKEN`, `DATABASE_PATH` и `HEALTH_FILE_PATH`. Предлагаемые defaults: `./data/temp-voice.sqlite` и файл состояния в системном временном каталоге. В Docker путь SQLite задаётся как `/data/temp-voice.sqlite`. Пути проверяются до подключения Discord; значения секретов в сообщениях ошибок не выводятся.

Конфигурация загружается на границе через `@nestjs/config`; потребители получают узкие неизменяемые Config. CLI восстановления и миграций загружает только настройки БД и не требует Discord token. Health-команда читает только свой файл состояния.

Уточнение подхода по проверенному пользователем примеру GoldGiverBackend: env-классы в `src/config/env/Variables` владеют дефолтами, преобразованием и проверками class-transformer/class-validator. Общие ValidateEnvGroup и ValidateEnv проверяют только необходимые точке входа группы. Модульные Config имеют private readonly поля и getters; injectable ConfigFactory реализуют FactoryInterface и используют `ConfigService<СвояГруппаEnv, true>`. Регистрация выполняется через CreateConfigProvider в scope потребителя, без отдельных ConfigurationModule и EnvironmentConfigService. Схема и правила размещения закреплены в разделе «Env и модульные Config» архитектуры проекта.

Корневые точки входа: `main.ts` / `bootstrap.ts` — бот, `console.ts` — операторские команды и health. Отдельная точка сборки `DatabaseDataSource.ts` предоставляет TypeORM CLI тот же набор моделей, миграций и параметров БД. Сборка списка моделей принадлежит composition root; технический Database принимает готовые options.

`App/Factory/DatabaseOptionsFactory.ts` получает DatabaseConfig, реализует TypeOrmOptionsFactory и подключается через useClass. ConfigFactory и Config регистрируются в extraProviders TypeORM. App/DatabaseOptionsModule использует те же фабрики и проверяет только DatabaseEnvVariables, предоставляя options операторскому CliModule и миграционной точке входа. Запуск миграций получает DataSource с `migrationsRun: false` и запускает миграции явно, без импорта CliModule и команд. Основной процесс и операторские команды сохраняют Nest Standalone.

## 4. SQLite и атомарность

Реализованы таблицы spec: `guild_settings`, `voice_triggers`, `temporary_channels`, `bot_owner`, `owner_codes`, `claim_attempts`, техническая отметка `pending_guild_removals` и история миграций. Схема создаётся двумя миграциями: InitialSchema1794586991484 и PendingGuildRemoval1794594323530. Операции Ownership используют существующие таблицы без новой миграции. Идентификаторы — строки, даты — целые миллисекунды UTC. Лимит — положительное целое либо NULL; командное значение 0 преобразуется в снятие ограничения.

У `voice_triggers` составной уникальный ключ `(guild_id, channel_id)`. У временных каналов первичный ключ `channel_id`, индексы по guild, исходному триггеру и создателю. Исходный триггер хранится как идентификатор без каскадного удаления временных каналов. `delete_attempts` хранит потраченный бюджет удаления.

Системные записи владельца и активного кода имеют по одному фиксированному ключу. Код содержит тип, хеш и nullable срок действия; попытки claim имеют ключ Discord User ID. Начальный и восстановительный коды действуют до использования или замены; срок передачи — 24 часа.

Общие options задают `synchronize: false`, `migrationsRun: false` для основного процесса, операторского CLI и миграционной точки входа. Миграции генерируются CLI в исходниках, проходят review и выполняются отдельными явными командами из скомпилированных файлов: migration:run применяет ожидающие миграции, migration:revert откатывает последнюю применённую. Оператор или процесс развёртывания выбирает момент и целевую версию; несколько шагов down требуют соответствующего числа явных revert. Подключение и запуск приложения не применяют и не откатывают миграции. Ошибка миграции завершает операцию подготовки БД отказом. CLI восстановления не выполняет предварительную проверку схемы и истории миграций: он обрабатывает ошибки своих запросов через существующий DatabaseOperationError.

up и down проектируются вместе как прямой и обратный переходы схемы и данных. Приоритет — сохранение данных и восстановление совместимости с предыдущей версией; неизбежные потери предварительно согласуются. Откат кода и откат БД управляются отдельно. Существующие down не изменялись этой правкой: InitialSchema возвращает пустую прикладную схему и удаляет её данные, PendingGuildRemoval удаляет таблицу pending_guild_removals вместе с её отметками. Эти последствия нужно учитывать до выбора такого отката; сохранность данных остальных шести таблиц при откате второй миграции проверена отдельно.

Для одного соединения better-sqlite3 используется `DatabaseOperationExecutor`: он последовательно выполняет целую короткую операцию Repository, включая её чтения и транзакцию. Это предотвращает пересечение транзакций и чтение промежуточного состояния через общий QueryRunner. Executor не получает бизнес-решения, Discord-запросы или ожидание пользовательских действий. Публичные методы Repository не вызывают друг друга через повторный вход в Executor.

WAL включён; ожидание блокировки ограничено 1 секундой. Между отдельными процессами основного бота и CLI согласованность обеспечивают SQLite и условные записи. Временная занятость БД — технический отказ, а не неправильная попытка claim. Ошибки сохранения не превращаются в успешный бизнес-результат.

OwnershipRepository объединяет тесно связанные системные таблицы и использует только операции EntityManager/QueryBuilder TypeORM. Авторизация получает owner ID одним SELECT. ReadCodeState получает ownerId, codeHash и isRedeemed одним LEFT JOIN от OwnerCode к BotOwner; отсутствие кода преобразуется в nullable значения в памяти. Код создаётся до владельца и сохраняется после погашения, поэтому агрегаты и поддержка состояния «владелец без кода» не нужны. Для claim код и попытки читаются с join; если кода нет, отдельно запрашиваются попытки. Запись выполняется условными update/delete либо insert, а не через save с дополнительным чтением. Hash и флаг погашения защищают от устаревшей замены кода без дополнительного чтения владельца. Успешный claim использует два SELECT: код с попытками и короткую проверку актуальных попыток в транзакции; полный снимок трёх таблиц не перечитывается. Погашение через isRedeemed = true, назначение владельца и сброс попыток остаются одной транзакцией. Новый код любого типа выставляет isRedeemed = false. Recovery атомарно заменяет код и удаляет владельца. Конкурирующая вставка обрабатывается как конфликт, техническая занятость БД не считается неверным кодом. До production начальная миграция повторно генерируется TypeORM с boolean-полем is_redeemed DEFAULT false; старую локальную БД можно пересоздать, перенос её данных не требуется.

Очистка данных покинутого guild использует публичные операции владельцев таблиц, выполняется идемпотентно и может быть продолжена после сбоя. Последовательность этих вызовов не объявляется общей транзакцией.

## 5. Очередь guild и актуальность событий

Создание, удаление, watch/unwatch, индивидуальные лимиты триггеров, AFK, очистка guild и сверка проходят через один экземпляр очереди по ключу guild ID. Общий лимит guild изменяется без ожидания этой очереди; чтение списков и пагинация также её не используют. В Core находится общий `KeyedOperationCoordinator`; бизнес-сервисы не получают объекты блокировок. Разные guild могут ожидать Discord независимо; краткие операции SQLite сериализуются отдельно.

Входные голосовые переходы получают последовательный номер. Смена канала и поколение состояния guild фиксируются при приёме события, до ожидания очереди. События без смены channel ID не создают канал. После ожидания проверяются текущий переход пользователя, активность триггера, cooldown и оба лимита. Старый вход не должен создать канал после выхода и нового входа в тот же триггер.

Для успешного watch фиксируется граница приёма событий. Входы, полученные до завершения регистрации, не превращаются в новые подключения из-за задержки очереди. Индивидуальный лимит можно сохранить до watch; при этом триггер остаётся неактивным.

После начального состояния guild новые входы сохраняются на время сверки. По завершении сверки обрабатываются актуальные входы; пользователь должен оставаться в исходном канале. Исходный snapshot, повторное подключение и уже завершённые входы не создают комнаты повторно.

## 6. Триггеры, лимиты и создание

Watch проверяет GuildVoice, отсутствие AFK-назначения и принадлежности к временным каналам, а также разрешения бота. Повтор активного watch возвращает результат без записи в БД. Unwatch оставляет индивидуальный лимит и существующие временные каналы; физическое удаление сбрасывает также лимит. Неактивная конфигурация удаляется только при отсутствии лимита и связанных каналов.

Проверка лимитов использует все сохранённые временные каналы, включая каналы удалённых триггеров и каналы с исчерпанным бюджетом удаления. Снижение лимита не удаляет существующие каналы. Cooldown — 5 секунд по `(guild_id, user_id)`, в памяти; отсчёт начинается после успешного перемещения.

Создание в очереди guild:

1. Проверить актуальность входа и бизнес-условия через Service.
2. Получить достоверные настройки триггера и проверить разрешения.
3. Вызвать публичный `client.rest.post(Routes.guildChannels(...))` discord.js с именем создателя, исходной категорией, совместимыми настройками и объединёнными permission overwrites. В 14.28.1 `guild.channels.create()` не сериализует необходимые flags; один POST передаёт все параметры вместе, без промежуточного канала с неполными настройками.
4. Сохранить channel ID, guild ID, исходный триггер, создателя и начальный бюджет удаления в SQLite.
5. Повторно проверить текущий вход и положение пользователя, затем переместить его.
6. Установить cooldown и сообщить об успешном результате в логах.

Адаптер копирует bitrate, user limit, RTC region, video quality mode, NSFW, slowmode голосового чата и применимые изменяемые flags, поддержанные API и выбранной версией SDK. Совместимые поля сверяются с типом GuildVoice. Имя ограничивается правилами API с сохранением корректной Unicode-строки; `position` не передаётся. `clone()` не используется, поскольку копирует позицию и не охватывает все требуемые поля.

В overwrite создателя добавляются только Allow ViewChannel, Connect и ManageChannels; соответствующие Deny снимаются. Остальные настройки триггера сохраняются. Отдельные права управления участниками бот не добавляет. Канал определяется по ID; его имя, положение и последующие изменения прав не используются для восстановления исходных настроек.

Основные разрешения бота — ViewChannel, ManageChannels, Connect и MoveMembers в соответствующих областях. Для полного копирования проверяется также возможность применить конкретные overwrites; если копирование невозможно, операция отклоняется с безопасным объяснением. Минимальные права подтверждаются на тестовом guild, без требования Administrator как общего условия.

Если пользователь ушёл или перемещение не удалось, используется общий сценарий удаления. При наличии других обычных пользователей канал сохраняется до опустения, cooldown не ставится. При отказе удаления запись и потраченный бюджет сохраняются.

Если после Discord create не удалось сохранить ID, выполняется безопасная компенсация по известному ID, а ошибка и ID отражаются в логах. Невозможность сохранить результат компенсации не скрывается. При необратимой ошибке БД процесс прекращает новые изменения, становится unhealthy и штатно завершается для последующего запуска. Уже согласованное окно аварии между create и записью ID остаётся ограничением ручной очистки; успех без записи в БД не объявляется.

## 7. Удаление и сверка

Удаление инициируется выходом пользователя, откатом или сверкой. Голосовой состав проверяется по текущим достоверным данным; боты не учитываются. Если сведения об участнике недостаточны для безопасного определения пустоты, канал не удаляется до получения достоверного состояния.

Перед запросом удаления проверяются запись, пустота и оставшийся бюджет. В SQLite условно резервируется одна попытка, после commit вызывается Discord DELETE. Незавершённая при аварии попытка остаётся потраченной. На один живой канал допускаются не более трёх таких запусков. Встроенные повторы REST SDK внутри одного вызова не являются новыми сценарными попытками.

После успеха или подтверждённого отсутствия удаляется запись; `channelDelete` делает то же идемпотентно. После отказа запись остаётся в лимитах. Немедленного цикла повторов нет: следующая попытка возможна на подходящем событии или сверке. Проверка отсутствия разрешена и при исчерпанном бюджете.

Для подтверждённого удаления бота из guild Voice сначала сохраняет `pending_guild_removals(guild_id)`, затем очищает данные через публичные Service Voice, Triggers и Limits и удаляет отметку. Прерванная очистка продолжается до Gateway login или до принятия повторно приглашённого guild. Недоступность guild и отсутствие в cache такую отметку не создают. Глобальные данные Ownership этой очистке не принадлежат.

Сверка выполняется после clientReady, восстановления Gateway и доступности guild. Она снимает недействующие триггеры, учитывает новый AFK-канал, очищает подтверждённо отсутствующие временные каналы и вызывает общий сценарий удаления пустых. Занятые каналы сохраняются.

Неполный cache, отсутствие в отфильтрованном списке каналов, Forbidden и недоступность guild не приравниваются к удалению. Отсутствие подтверждается доступным достоверным ответом API или соответствующим Gateway-событием. Периодического REST-опроса нет.

## 8. Команды и представление

Обе группы команд регистрируются глобально с GuildInstall. `/voice` имеет context Guild и default permissions ManageGuild; `/owner` — context BotDM. Группы описываются на классах через `@SlashCommand`, методы — через `@Subcommand`. Observer объединяет связанные события по роли; отдельный класс на каждое событие не требуется.

Necord использует `skipRegistration: true`. Сервис синхронизации получает определения из discovery Necord, нормализует управляемые поля и сравнивает их с Discord. Служебные ID, version и различие отсутствующих необязательных полей не создают ложных изменений. При совпадении запись не выполняется; изменения применяются адресно. Второй источник описаний команд не создаётся.

Простые guards проверяют транспортный контекст и доступные permissions. Slash-команды с длительной работой подтверждают получение через defer до ожидания очереди и БД. Проверка актуального владельца выполняется один раз при принятии команды, до ожидания очереди guild. Принятая команда завершается после смены владельца, включая время ожидания; следующая команда и клик проверяют новое владение.

Реализация T062 с уточнением T065: OwnerCommandController использует публичный OwnershipService при принятии команды. WatchTriggerHandler, UnwatchTriggerHandler, SetChannelLimitHandler и GetVoiceListHandler не принимают ID глобального владельца и не зависят от Ownership; они проверяют текущую доступность guild через VoiceChannelGatewayInterface. Discord-модуль проверяет введённые ID и не раскрывает данные владельца посторонним. CommandOptionsPipe создаёт экземпляр класса options DTO поверх полей Necord, сохраняя вложенные объекты SDK по ссылке; глубокое преобразование VoiceChannel не выполняется. Общий CommandExceptionFilter переводит отказы в безопасные локализованные сообщения.

Autocomplete повторно проверяет пользователя и принадлежность guild/channel, использует достоверный cache и возвращает до установленного Discord количества вариантов. Ручной ввод ID проходит те же проверки. При невозможности ответить вовремя возвращается пустой результат без раскрытия чужих данных.

Ответы guild — ephemeral, DM — обычные. Русский ответ выбирается для Locale.Russian, иначе английский. Описания команд и параметров имеют RU-локализацию; имена команд сохраняются согласно spec. Ошибки преобразуются в локализованный ответ на транспортной границе; логируются только безопасные поля.

Пагинация хранит снимок списка, автора и время истечения в памяти. Каждая кнопка задаёт целевую страницу; повторные нажатия той же кнопки показывают ту же страницу без накопления переходов. Изменяемого счётчика страницы и очереди пагинации нет. Срок — 15 минут без продления при кликах. Кнопки проверяют автора, доступ, срок и границы страницы. После перезапуска или истечения срока возвращается сообщение о недействующей сессии. Формат custom ID и размер страницы учитывают ограничения Discord.

GetVoiceListHandler читает данные через публичные Service Triggers, Limits и Voice без ожидания очереди guild. Количество включает все сохранённые комнаты; комнаты без активного триггера и исчерпавшие три попытки удаления выделяются отдельно. Общий лимит запрашивается только для списка владельца; guild-команда не выполняет это чтение. Discord-представление добавляет владельцу общую статистику и неактивные конфигурации с лимитами. CommandListService хранит страницы только в памяти, подтверждает клики до авторизации владельца и заново проверяет права при перелистывании. Autocomplete отдаёт максимум 25 вариантов из доступного cache; при невозможности закончить авторизацию за 2 секунды отвечает пустым списком.

## 9. Владение и CLI

Коды состоят из 32 криптографически случайных латинских букв и цифр. Для высокоэнтропийного кода используется SHA-256; сравнение хеша — constant-time. Код передаётся только нужному получателю: начальный — оператору через stdout основного процесса, передача — владельцу в DM, восстановление — оператору в stdout CLI.

Передача оставляет текущего владельца до успешного claim и заменяет предыдущий код передачи; срок — 24 часа. До первого назначения обычные guild-команды работают. При запуске без владельца создаётся новый начальный код, аннулирующий предыдущий.

Claim сохраняет запись кода с isRedeemed = true; погашенный код отвергается и после перезапуска. Начальный, transfer и recovery код создаются с isRedeemed = false. Этот флаг хранится вместе с хешем и изменяется атомарно с владельцем.

Конфликт начальной генерации OwnershipBootstrapObserver обрабатывает предупреждением и продолжает запуск без повторной попытки: уже сохранённый результат другой операции не перезаписывается, несохранённый код не выводится. Технические ошибки БД при инициализации пробрасываются.

Пять неправильных кодов на User ID блокируют проверку на 15 минут. Во время блокировки код не проверяется. По окончании доступны новые пять ошибок; успешный claim сбрасывает ошибки и блокировку этого пользователя. Состояние сохраняется в SQLite. Технический отказ БД не считается неправильным кодом.

`owner:recover` запускает отдельный контекст с конфигурацией БД, Logging и Ownership. В одной операции заменяются владелец и активный код. Код выводится после commit, не передаётся параметром командной строки и не включается в обычные логи. Повтор recovery заменяет предыдущий восстановительный код. CLI закрывает DataSource и возвращает ненулевой exit code при ошибке.

Уточнение пользователя 2026-11-16: операторские команды описываются через nest-commander, отдельными CommandRunner с декоратором Command. console.ts запускает CommandFactory и не содержит маршрутизации по argv или вызовов Ownership. Обработчик команды получает зависимости через DI; CommandFactory закрывает контекст после исполнения, включая ошибки парсинга и help. Имя owner:recover и контракт восстановления сохраняются.

Гонки claim/claim, claim/recovery и transfer/recovery проверяются на реальной SQLite, включая отдельные процессы, поскольку локальная очередь не доказывает этот инвариант. Используются условные атомарные изменения; открытые транзакции не содержат Discord-запросов.

## 10. Готовность, завершение и эксплуатация

Главный процесс раз в 5 секунд после успешной локальной проверки БД атомарно обновляет небольшой health-файл: PID, время обновления, готовность Gateway и результат начальной сверки. Файл не находится на постоянном Volume и не содержит секретов. Новое выполнение сбрасывает готовность до загрузки состояния.

Health-команда не создаёт Nest context и Discord Client: она проверяет файл, живой PID, готовность и свежесть не более 15 секунд. При зависшем event loop обновление прекращается. Это локальная проверка без HTTP и REST-опроса Discord. Окончательные интервалы подтверждаются при Docker-приёмке.

При shutdown снимается готовность, прекращается допуск новых операций, выполняющиеся сценарии завершаются с компенсацией в пределах 15 секунд. Только затем освобождаются Discord и SQLite. Истечение времени не делает незавершённый сценарий успешным; сохранённое состояние обрабатывается при следующем запуске. Порядок hooks проверяется с учётом того, что Necord и TypeORM имеют собственное закрытие ресурсов.

Docker использует multi-stage сборку и Node.js 24 на Debian slim. Зависимости better-sqlite3 устанавливаются для целевой архитектуры, runtime получает скомпилированный код, миграции и production dependencies. Образ проверяется для linux/amd64 и linux/arm64. SQLite хранится в Volume `/data`, рабочий процесс имеет права записи; health-файл временный.

По уточнению пользователя финальный слой формируется явным копированием только необходимых runtime-артефактов: dist приложения и CLI, скомпилированных миграций, production node_modules, нативных библиотек и метаданных запуска. DevDependencies, исходники и тесты проекта, coverage, документация разработки, инструменты компиляции, кэши и настройки редактора в финальный слой не копируются. Production-зависимости подготавливаются отдельно с исключением devDependencies; toolchain для better-sqlite3 остаётся на промежуточном этапе. .dockerignore исключает локальные node_modules, .git, .env, БД, логи и прочие артефакты разработки из контекста. В runtime не выполняются npm install, npm ci или build. При Docker-приёмке проверяются состав образа и запуск приложения, CLI и явных миграций без инструментов разработки.

Compose использует `restart: unless-stopped`, локальный healthcheck и `json-file` с max-size 10m / max-file 3. Предлагаемые параметры healthcheck: interval 10s, timeout 3s, retries 3, start_period 60s. Состояние unhealthy само по себе не заменяет reconnect discord.js и не считается успешным деплоем.

CI на размещённых GitHub runners выполняет typecheck, lint, Vitest и build для PR, main и релизного тега. Релиз допускается только для `vX.Y.Z` на коммите из истории main; после проверок публикуются multi-arch образы версии и latest. Deployment идёт отдельным job на явно выбранном self-hosted runner, обновляет `.deploy.env`, выполняет pull/up и ожидает healthy. Автоматического rollback нет.

До настройки deployment понадобятся сведения о runner и доступе к GHCR; это входные данные этапа развёртывания, а не предположение об уже работающем сервере. Проверки непроверенных PR не получают доступ к Docker-хосту.

## 11. Проверка и документация

Бизнес-тесты выполняются без Discord и покрывают правила spec, включая новые уточнения. Для конкурентного владения используются интеграционные проверки SQLite. Техническая совместимость и SDK проверяются ручными smoke-проверками; тесты обычного CRUD, DI wiring и конфигурационных значений ради покрытия не добавляются.

Отдельная приёмка с настоящим Discord подтверждает разрешения, копирование настроек, DM-команды, RU/EN, кнопки, reconnect и сохранность занятых каналов. Docker-приёмка подтверждает обе архитектуры, сохранность Volume, миграции на существующей БД, зависший процесс и успешный/неуспешный deployment.

README и инструкции описывают создание Discord Application, приглашение, минимальные права, настройки окружения, первоначальный код, recovery, запуск, обновление, ручной backup и выпуск тега. Для ручного backup используется поддержанный SQLite Backup API; простое копирование одного файла работающей WAL-БД не объявляется корректным backup.

Критерий завершения feature: выполнены задачи, релевантные бизнес-тесты, lint, typecheck и build; критерии spec проверены в указанной среде, а неподтверждённые интеграции явно перечислены. Статус сборки не выдаётся за успешный деплой.
