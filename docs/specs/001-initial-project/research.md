Дата проверки: 2026-11-13. Требования — [spec.md](spec.md), технический план — [plan.md](plan.md).

## Среда и границы проверки

Проверка выполнена в отдельном временном каталоге вне репозитория, на Windows x64 с Node.js 24.22.1 и npm 11.19.1. Зависимости приложения в репозитории не устанавливались. Discord token не использовался, реальное подключение к Gateway и публикация команд не выполнялись.

Для проверки собиралось небольшое приложение Nest Standalone. Только подключение клиента к Discord было подменено; Nest DI, декораторы Necord, guard, TypeORM и SQLite выполнялись настоящие.

## Necord и команды

`NecordModule` подключает клиент в `onApplicationBootstrap`. Первоначальный изолированный запуск проверял автоматические миграции до этой фазы. Уточнение пользователя T056 отменило этот режим: актуальное подключение не выполняет миграции, БД подготавливается отдельной явной операцией. Исторический результат проверки lifecycle выше не является текущей политикой запуска.

Автоматическая регистрация Necord после `clientReady` вызывает `application.commands.set()` без сравнения с текущими определениями. Для требования spec «синхронизировать только при изменениях» выбирается `skipRegistration: true` и собственная синхронизация: получить определения Necord, сравнить нормализованные управляемые поля с Discord и обновить только изменившиеся команды. Ручной второй набор определений команд не создаётся.

`@SlashCommand` можно применять к классу, методы группы отмечаются `@Subcommand`. Корневая метаинформация сохраняет `contexts`, `integrationTypes` и локализации. Для `/voice` планируется контекст guild, для `/owner` — DM бота; обе группы регистрируются глобально для guild-installed приложения.

Проверены [описание команд](https://necord.js.org/interactions/slash-commands), [SlashCommandDiscovery](https://github.com/necordjs/necord/blob/master/src/commands/slash-commands/slash-command.discovery.ts), [запуск регистрации](https://github.com/necordjs/necord/blob/master/src/commands/commands.module.ts), [обновление команд](https://github.com/necordjs/necord/blob/master/src/commands/commands.service.ts) и [контексты Discord](https://docs.discord.com/developers/interactions/application-commands#contexts).

## SQLite и конкурентные операции

В опубликованном `typeorm@1.1.3` файл `driver/better-sqlite3/BetterSqlite3Driver.js` возвращает один QueryRunner. `EntityManager.transaction()` не создаёт независимое соединение для каждого параллельного вызова. Поэтому очереди guild недостаточно: операции разных guild и Ownership могут пересекаться на одном соединении.

План должен отдельно обеспечить последовательное выполнение коротких операций Repository на этом соединении. При этом сетевые запросы Discord выполняются вне очереди SQLite и вне транзакции. Между основным процессом и CLI действуют блокировки SQLite и условные записи; очередь в памяти одного процесса их не заменяет.

Выбранный драйвер поддерживает WAL и ожидание блокировки. Коды при claim/transfer/recovery должны проверяться и погашаться с защитой от изменения сохранённого состояния между чтением и записью. Проверяется бизнес-инвариант однократного назначения владельца, а не работа обычного CRUD драйвера.

Источники: опубликованный пакет TypeORM 1.1.3, [SQLite driver](https://typeorm.io/docs/drivers/sqlite/), [транзакции](https://typeorm.io/docs/advanced-topics/transactions/).

## Разрешения и достоверность данных Discord

Создание канала требует `ManageChannels`; копировать permission overwrites можно только в пределах разрешений, доступных боту. Поэтому фиксированный список основных permissions дополняется проверкой копируемых overwrites конкретного триггера. Неполное копирование вместо отказа не допускается.

Список каналов и локальный cache не считаются доказательством удаления при потере доступа. Discord документирует дополнительную фильтрацию списка каналов по видимости с 2026-11-16. Сверка должна различать подтверждённое отсутствие, недоступность guild и неизвестное состояние из-за прав.

Источник: [Create Guild Channel и Get Guild Channels](https://docs.discord.com/developers/resources/guild#create-guild-channel). Применимые поля голосового канала фиксируются по API и версии SDK при реализации; имя и позиция обрабатываются по исключениям spec.

В опубликованном `discord.js@14.28.1` метод `GuildChannel.clone()` передаёт `position: this.rawPosition` и не копирует все необходимые голосовые поля. При реализации также проверен `GuildChannelManager.create()`: он не принимает и не сериализует flags. Поэтому адаптер использует публичный `client.rest.post(Routes.guildChannels(...))` с `RESTPostAPIGuildChannelJSONBody`, одним запросом без `position`. Для GuildVoice копируется изменяемый `IsSpoilerChannel`; `ChannelObfuscated` обозначает недоступные данные и не копируется. Типы и enum берутся из публичных экспортов discord.js.

Состав определяется по актуальному voice-state cache доступного guild. Неизвестная принадлежность участника к ботам и потеря ViewChannel означают Unknown, а не пустоту. Прямой UnknownChannel (10003) считается отсутствием только в прежнем доступном поколении guild; отказ доступа, обфускация и пропажа cache таким доказательством не служат. При копировании overwrites проверяются все Allow/Deny и добавляемые права создателя; установка ManageRoles в overwrite требует Administrator, но общего требования Administrator для работы бота нет.

`GuildChannelManager.delete()` после REST вызывает `ChannelDeleteAction`, который синхронно доставляет `channelDelete`. Вход Observer отделяется от AsyncLocalStorage-контекста исходного сценария: отдельное уведомление ставится в очередь, не наследуя владение текущей операцией. Локальная проверка через настоящие listeners Necord обнаружила этот случай; после исправления добавлен регрессионный бизнес-тест.

Дополнительные источники: [Channel flags](https://docs.discord.com/developers/resources/channel#channel-object-channel-flags), [коды ошибок Discord](https://docs.discord.com/developers/topics/opcodes-and-status-codes#json-json-error-codes), опубликованные исходники discord.js 14.28.1 и Necord 7.1.1. Реальные права и поведение Discord API требуют отдельной проверки на тестовом guild.

## Миграция ESLint 10 с сохранением правил

По отдельному решению владельца проекта используется ESLint 10 с сохранением автоматических проверок. `eslint-plugin-explicit-exceptions@0.13.3` объявляет peer ESLint `^9.27.0`, но его исполняемый код использует современный API. Проверка подтвердила работу плагина на ESLint 10.14.0 без изменения исходников и адаптеров совместимости.

Для установки используется только адресный override `eslint-plugin-explicit-exceptions.eslint: "$eslint"`. Глобальные `--force` и `--legacy-peer-deps` не используются. `npm ls eslint` подтверждает один ESLint 10.14.0 во всём дереве. Это проверенная совместимость выбранных версий, а не заявление об официальной поддержке ESLint 10 автором плагина.

На исходной конфигурации ESLint 9 зафиксированы результаты 27 примеров, затем те же входы проверены на ESLint 10. Совпали сообщения правил и результаты всех 12 проверенных автоисправлений:

- базовые recommended-правила и TypeScript recommended;
- фигурные скобки, пустые строки перед return и вокруг многострочных операторов;
- неиспользуемые переменные и исключения с подчёркиванием;
- сортировка импортов, отдельные type-only импорты, запрет inline type и сохранение порядка side effects;
- отсутствие `@throws` у синхронного и асинхронного throw, проброс известных ошибок через вызовы;
- соответствие типов в `@throws`, обязательный тип и разрешимость его имени;
- корректные синхронные/асинхронные контракты, поглощённые ошибки и import type, используемый только документацией;
- исключение `*.spec.ts` из проверки контракта ошибок и игнорирование dist/coverage.

В проекте дополнительно проверены scoped globals Vitest вместо Jest, включённый projectService для production TypeScript и компиляция временных примеров через корневой tsconfig. Проверочные файлы удалены; технические тесты библиотек в приложении не добавлены. Синтаксический запрет inline type остаётся диагностикой без собственного автоисправления, как в исходной конфигурации.

Команды проекта `lint` и `format:check` проходят. `lint:fix` применяет исправления ESLint, `format` — исправления ESLint и затем Prettier. Ранее известные ограничения полноты анализа исключений не устранены миграцией; review контракта ошибок остаётся обязательным.

Источники: опубликованные метаданные и исходники плагина, [миграция ESLint 10](https://eslint.org/docs/latest/use/migrate-to-10.0.0), [npm overrides](https://docs.npmjs.com/cli/v11/configuring-npm/package-json#overrides).

## nest-commander для операторского CLI — 2026-11-16

По уточнению пользователя выбран nest-commander 3.21.0: его опубликованный peer-диапазон включает Nest 12. Пакет закрепляет @golevelup/nestjs-discovery 7.0.3, чей peer-диапазон ограничен Nest 11; первоначальная установка поэтому дала предупреждение, а npm ls — несовместимость. У discovery 7.1.0 заявлена поддержка Nest 12. В package.json добавлен адресный override только для этой зависимости nest-commander, затем обновлён lockfile; повторный npm ls проходит без несовместимых peers. Версии проверены через npm view и установленные package.json, без force или legacy-peer-deps.

В исходниках установленной версии подтверждено: CommandFactory.run закрывает контекст в finally, но стандартный process.exit Commander обходит это завершение. Для управляемого выхода настроены errorHandler/serviceErrorHandler фабрики и exitOverride команды. Встроенный Commander 11.1.0 по умолчанию допускает лишние позиционные аргументы; OwnerRecoverCommand отключает это через публичный setCommand/allowExcessArguments, чтобы неверный вызов не запускал recovery. Парсинг остаётся в библиотеке.

Проверены строгая компиляция, Nest DI и восемь отдельных запусков готового CLI: recovery, повтор recovery, глобальный и командный help, неизвестная команда, лишние аргументы, SQLite busy и немигрированная БД. Во всех случаях подтверждено закрытие DataSource без Discord login. Существующие бизнес-сценарии сохранены; результаты — в [verification.md](verification.md).

Источники API: [CommandFactory](https://nest-commander.jaymcdoniel.dev/en/features/factory/), [документация Nest](https://docs.nestjs.com/recipes/nest-commander). Совместимость конкретных версий дополнительно проверена по метаданным npm и исходникам установленных пакетов.
