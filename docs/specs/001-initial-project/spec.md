# TempVoice — техническое задание

**Статус:** требования согласованы, готово к разработке  
**Тип:** Discord-бот для автоматического создания временных голосовых каналов  
**Лицензия:** MIT  
**Репозиторий:** `temp-voice`

---

## 1. Назначение проекта

TempVoice — мультисерверный Discord-бот, автоматически создающий временные голосовые каналы при подключении пользователя к зарегистрированному каналу-триггеру.

Бот должен:

- Создавать персональные голосовые каналы с правами управления для их создателей.
- Автоматически удалять каналы, когда в них не остаётся обычных пользователей.
- Поддерживать несколько триггеров в каждом guild и несколько guild одновременно.
- Позволять администраторам guild управлять триггерами через slash-команды.
- Предоставлять глобальному владельцу бота управление триггерами и лимитами всех guild через DM.
- Сохранять состояние при перезапусках и обновлениях.
- Минимизировать обращения к Discord REST API.

Веб-интерфейс, HTTP API и отдельная панель администрирования не требуются.

## 3. Каналы-триггеры

### 3.1. Регистрация

Администратор guild регистрирует голосовой канал командой `/voice watch`.

Требования:

1. Триггером может быть только обычный голосовой канал `GuildVoice`.
2. `GuildStageVoice` не поддерживается.
3. Текущий AFK-канал guild нельзя регистрировать.
4. Временный канал, ранее созданный TempVoice, нельзя зарегистрировать как триггер.
5. Повторная регистрация уже активного триггера возвращает сообщение без изменения SQLite.
6. Перед регистрацией проверяются необходимые разрешения бота.
7. После регистрации обработке подлежат только новые подключения. Пользователей, уже находящихся в триггере, не перемещать.

При назначении зарегистрированного триггера AFK-каналом наблюдение автоматически снимается.

### 3.2. Снятие наблюдения

Команда `/voice unwatch` удаляет триггер из активного наблюдения.

- Новые временные каналы больше не создаются.
- Существующие каналы продолжают работать.
- Занятые каналы не удаляются принудительно.
- Каждый существующий временный канал удаляется после выхода последнего обычного пользователя.

**Физическое удаление триггера из Discord должно иметь такую же логику относительно временных каналов.**

Разница касается настроек: при физическом удалении триггера его индивидуальный лимит удаляется, а при `/voice unwatch` сохраняется.

### 3.3. Изменение триггера

При перемещении триггера в другую категорию новые каналы создаются в новой категории. Существующие остаются на прежних местах.

Изменение прав и настроек триггера не синхронизируется с уже созданными временными каналами.

## 4. Создание временного канала

### 4.1. Условия

Создание запускается при любом попадании обычного пользователя в зарегистрированный триггер:

- Первоначальное подключение.
- Переход из другого голосового канала.
- Принудительное перемещение администратором.

Боты не активируют триггеры.

Для создания должны выполняться условия:

1. Триггер активен.
2. Пользователь не является ботом.
3. Для пользователя не действует cooldown.
4. Не достигнут лимит guild.
5. Не достигнут лимит триггера.
6. Бот располагает необходимыми разрешениями.

Если лимит достигнут, пользователь остаётся в триггере. Причина записывается в логи.

### 4.2. Последовательность

1. Получить `voiceStateUpdate`.
2. Определить новый `channel_id`.
3. Проверить регистрацию триггера в SQLite.
4. Проверить cooldown и лимиты.
5. Считать актуальные настройки триггера.
6. Создать обычный голосовой канал в той же категории.
7. Скопировать настройки и разрешения.
8. Добавить индивидуальные разрешения создателю.
9. Сохранить информацию о временном канале в SQLite.
10. Проверить, что пользователь всё ещё находится в исходном триггере.
11. Переместить пользователя в созданный канал.
12. Зафиксировать успешную операцию и установить cooldown.

Ограничение первой версии: аварийное завершение процесса после создания канала в Discord, но до сохранения его ID в SQLite может оставить неучтённый канал. Такой редкий случай допускает ручное удаление оператором; автоматическое обнаружение и очистка не гарантируются. Имя канала не используется для поиска или идентификации такого канала.

Если пользователь покинул триггер до перемещения, операция отменяется.

Если перемещение завершилось ошибкой, созданный канал удаляется. Неуспешный откат обрабатывается общим механизмом удаления с сохранением записи в SQLite.

Если к моменту отката в созданный канал уже вошли другие обычные пользователи, канал сохраняется до выхода последнего из них. Запись остаётся в SQLite и учитывается в лимитах; cooldown создателю не устанавливается.

### 4.3. Настройки канала

Копировать все совместимые настройки голосового триггера, включая:

- Permission overwrites.
- Bitrate.
- User limit.
- RTC region.
- Video quality mode.
- Другие применимые свойства, поддерживаемые используемой версией Discord API.

Исключения:

- **Имя:** серверный никнейм создателя, при отсутствии — его отображаемое имя Discord.
- **Позиция:** определяется Discord, бот не переставляет каналы.
- **Права создателя:** добавляются отдельно.

Имя ограничивается требованиями Discord API. Оно не сохраняется в SQLite, не отслеживается и не используется для идентификации канала.

### 4.4. Права создателя

Добавить индивидуальный permission overwrite:

| Permission | Значение |
|---|---|
| `ViewChannel` | Allow |
| `Connect` | Allow |
| `ManageChannels` | Allow |

Не выдавать:

- `MuteMembers`.
- `MoveMembers`.
- Глобальный `Administrator`.
- Другие права управления участниками.

`ManageChannels` должен предоставляться только на созданный временный канал. Создатель может изменять его название, битрейт, лимит участников и удалять сам канал.

Бот не восстанавливает права, изменённые администратором после создания.

### 4.5. Владение каналом

- Создатель сохраняет индивидуальные права после выхода из голосового канала.
- Владение автоматически не передаётся.
- Если создатель покинул guild, канал продолжает существовать до опустения.
- Один пользователь может одновременно иметь несколько временных каналов.
- Каждый новый вход в триггер создаёт новый канал при соблюдении cooldown и лимитов.

### 4.6. Cooldown

После успешного создания канала устанавливается cooldown **5 секунд**.

Ключ ограничения: `(guild_id, user_id)`.

Cooldown:

- Работает независимо от того, какой триггер использован.
- Хранится только в оперативной памяти.
- Не устанавливается после неудачного создания.
- Не препятствует созданию каналов другими пользователями.

## 5. Удаление временных каналов

### 5.1. Автоматическое удаление

При выходе участника бот проверяет, зарегистрирован ли покинутый канал как временный.

Если зарегистрирован, проверяется число оставшихся обычных пользователей.

**Канал удаляется, когда количество обычных пользователей равно нулю.**

Боты при определении пустоты не учитываются.

После успешного удаления из Discord удаляется запись из SQLite, освобождая соответствующие слоты лимитов.

Если канал самостоятельно удалён пользователем или администратором, бот обрабатывает `channelDelete` и очищает SQLite.

### 5.2. Неудачное удаление

Для каждого временного канала допускается максимум **3 автоматические попытки удаления за всё время его существования**. Успешное удаление завершает жизненный цикл канала.

- Потраченная попытка сохраняется в SQLite перед запросом удаления к Discord.
- Перезапуск не сбрасывает счётчик.
- Если процесс завершился после записи попытки, но до получения результата удаления, попытка остаётся потраченной, даже если запрос ещё не успел начаться.
- Попытки могут происходить при штатных событиях и последующих сверках.
- Периодический опрос REST API не используется.
- После исчерпания трёх попыток автоматическое удаление прекращается.
- Проблемный канал остаётся в БД и продолжает учитываться в лимитах.

Администратор может вручную удалить такой канал в Discord. После получения события удаления бот очищает запись.

Если при сверке обнаружено, что канала уже нет в Discord, соответствующую запись можно удалить независимо от числа потраченных попыток.

### 5.3. Смена категории

Если администратор переместил временный канал в другую категорию, бот продолжает управлять им без перемещения обратно.

## 6. Лимиты

### 6.1. Два уровня

**Guild limit** — общее максимальное количество временных каналов guild.

**Trigger limit** — максимальное количество временных каналов, связанных с конкретным триггером.

Индивидуальный лимит можно задать заранее для подходящего голосового канала до `/voice watch`. Настройка сохраняется как неактивная и сама по себе не включает создание временных каналов.

Оба ограничения действуют одновременно.

По умолчанию лимиты отсутствуют.

Значение `0` в команде настройки означает снятие ограничения. В SQLite отсутствие ограничения представляется `NULL` или отсутствием соответствующей записи, а не нулевым лимитом.

### 6.2. Подсчёт

Учитывать все существующие временные каналы:

- Активных триггеров.
- Триггеров, снятых с наблюдения.
- Триггеров, физически удалённых из Discord.
- Проблемные каналы, которые не удалось удалить.

После повторной регистрации прежнего триггера его сохранившиеся временные каналы продолжают учитываться.

При снижении лимита ниже текущего количества каналов существующие каналы не удаляются. Создание новых блокируется до освобождения слотов.

### 6.3. Сохранение настроек

После `/voice unwatch` индивидуальный лимит сохраняется.

Неактивная конфигурация автоматически удаляется, если одновременно:

- Триггер неактивен.
- Нет связанных временных каналов.
- Не установлен индивидуальный лимит.

Физическое удаление триггера удаляет его настройку лимита, но не временные каналы.

## 7. Slash-команды

Команды регистрируются автоматически при запуске. Синхронизировать определения только при наличии изменений.

Поддерживаются русская и английская локализации описаний и ответов. Английский используется по умолчанию.

### 7.1. Команды `/voice`

Доступны только внутри guild пользователям с `ManageGuild`.

| Команда | Назначение |
|---|---|
| `/voice watch channel` | Регистрация триггера |
| `/voice unwatch channel` | Снятие наблюдения |
| `/voice list` | Список триггеров |

Параметр `channel` выбирается стандартным селектором Discord с ограничением типа `GuildVoice`.

Все ответы — ephemeral.

### 7.2. Команды `/owner`

Доступны только в личных сообщениях боту.

| Команда | Назначение |
|---|---|
| `/owner claim code` | Активация код-фразы |
| `/owner transfer` | Генерация кода передачи владения |
| `/owner watch guild channel` | Регистрация триггера на выбранном guild |
| `/owner unwatch guild channel` | Снятие наблюдения |
| `/owner list guild` | Список триггеров и статистика |
| `/owner limit guild limit [channel]` | Установка лимита guild либо триггера |

`claim` доступна любому пользователю, остальные команды — исключительно текущему владельцу бота.

Параметры `guild` и `channel` реализуются как строковые параметры с Autocomplete. Их значения — Discord Snowflake ID, а пользователю отображаются читаемые названия.

Все введённые значения повторно проверяются серверной логикой, независимо от результатов Autocomplete.

В DM ответы обычные, не ephemeral.

### 7.3. Списки

`/voice list` показывает:

- Активные триггеры.
- Количество временных каналов по каждому.
- Индивидуальные лимиты.
- Отдельное количество каналов без активного триггера.
- Проблемные каналы и их упоминания для ручного удаления.

`/owner list` дополнительно показывает:

- Общий лимит guild.
- Суммарное количество временных каналов.
- Неактивные триггеры с сохранёнными лимитами.

Длинные списки разбиваются на страницы с кнопками «Назад» и «Далее».

Каждая кнопка задаёт конкретную целевую страницу. Повторное нажатие той же кнопки показывает ту же страницу без накопления переходов. Чтение списков, пагинация и изменение общего лимита guild не ждут очередь создания комнат.

Кнопки действуют **15 минут**, доступны только вызвавшему команду. Состояние пагинации хранится в памяти. После перезапуска старые кнопки не восстанавливаются.

## 8. Глобальный владелец TempVoice

### 8.1. Первоначальная активация

До назначения владельца бот продолжает работать: администраторы guild могут управлять триггерами.

При запуске без назначенного владельца:

1. Генерируется криптографически случайный код из 32 латинских букв и цифр.
2. В SQLite сохраняется только его хеш.
3. Ранее сгенерированный код аннулируется в той же операции сохранения.
4. После успешного сохранения код выводится в Docker-логи.
5. Пользователь вводит `/owner claim code` в DM.
6. При успешной проверке его Discord User ID становится глобальным владельцем.
7. Код немедленно погашается: запись сохраняется с флагом `is_redeemed = true`, повторное использование невозможно.

Одновременно может существовать только один владелец.

Запись кода появляется до первого владельца и сохраняется после claim. Начальный код, код передачи и recovery заменяют содержимое этой записи и сбрасывают флаг погашения в false. Назначение владельца, погашение кода и сброс попыток пользователя выполняются одной транзакцией. Совместимость со старой локальной БД, где claim удалял код, не требуется: до первого production-развёртывания её можно пересоздать.

Если при первоначальной генерации другой процесс успел изменить владельца или код, бот сохраняет результат той операции и продолжает запуск с предупреждением. Повторная генерация при таком конфликте не выполняется, несохранённый код не выводится. Ошибка самой БД остаётся отказом инициализации.

### 8.2. Передача владения

1. Текущий владелец выполняет `/owner transfer` в DM.
2. Бот создаёт новую одноразовую код-фразу.
3. Предыдущий неиспользованный код передачи аннулируется.
4. Новый код действует **24 часа**.
5. Владелец передаёт код будущему владельцу.
6. Получатель выполняет `/owner claim code`.
7. В одной транзакции SQLite проверяется и погашается код, после чего назначается новый владелец.

Прежний владелец немедленно теряет глобальные полномочия.

Права глобального владельца проверяются один раз при принятии команды. Принятая команда выполняется до конца, включая ожидание очереди операций guild, даже если затем владелец сменился. Новые команды, запросы Autocomplete и нажатия кнопок проходят собственную проверку доступа; повторная проверка владельца внутри уже принятой команды не выполняется.

Отдельная команда отмены передачи не требуется: повторный `/owner transfer` аннулирует предыдущий код.

### 8.3. Защита кодов

- Максимум 5 неправильных попыток на Discord User ID.
- После достижения лимита проверка кодов блокируется на 15 минут.
- Счётчики и блокировки хранятся в SQLite.
- По окончании 15-минутной блокировки пользователю снова доступны 5 неправильных попыток.
- Успешный claim сбрасывает счётчик ошибок и блокировку этого пользователя.
- Код-фразы не логируются при проверке.
- Проверка хеша выполняется безопасным способом.
- Код нельзя использовать повторно.

### 8.4. Восстановление владельца

При утрате доступа к Discord-аккаунту владельца предусмотрена отдельная команда Docker CLI.

Команда:

- Аннулирует текущее владение и активные коды.
- Генерирует новую одноразовую код-фразу.
- Выводит её оператору в stdout CLI-команды; в Docker-логи код восстановления не записывается.
- Позволяет назначить нового владельца через `/owner claim`.

Восстановление требует доступа к Docker-хосту.

## 9. Модель данных SQLite

Предлагаемые таблицы:

### `guild_settings`

| Поле | Назначение |
|---|---|
| `guild_id` | Primary key |
| `channel_limit` | Nullable общий лимит |

### `voice_triggers`

| Поле | Назначение |
|---|---|
| `guild_id` | Discord guild ID |
| `channel_id` | ID триггера |
| `is_active` | Состояние наблюдения |
| `channel_limit` | Nullable индивидуальный лимит |
| `created_at` | Дата регистрации |

Составной уникальный ключ `(guild_id, channel_id)`.

### `temporary_channels`

| Поле | Назначение |
|---|---|
| `channel_id` | Primary key, Discord ID |
| `guild_id` | Guild временного канала |
| `trigger_channel_id` | ID исходного триггера |
| `owner_id` | ID пользователя-создателя |
| `delete_attempts` | Число потраченных автоматических попыток удаления |
| `created_at` | Дата создания |

Связь с триггером не должна приводить к каскадному удалению временных каналов при удалении записи триггера.

### Системные таблицы

- `bot_owner` — единственный текущий владелец.
- `owner_codes` — хеш и срок действия текущей код-фразы, её тип и флаг погашения `is_redeemed` (по умолчанию false).
- `claim_attempts` — счётчики ошибок и время окончания блокировки.
- Служебная таблица истории миграций TypeORM.

Discord ID хранить как строки, чтобы исключить потерю точности Snowflake.

Схема должна иметь индексы для поиска временных каналов по guild, триггеру и владельцу.

## 10. События Discord

| Событие | Действие |
|---|---|
| `voiceStateUpdate` | Создание канала, отслеживание выхода участников |
| `channelDelete` | Очистка записей удалённых каналов |
| `channelUpdate` | Отслеживание применимых изменений триггера, без восстановления пользовательских прав |
| `guildUpdate` | Обработка изменений AFK-канала |
| `guildDelete` | Очистка данных после удаления бота из guild |
| `interactionCreate` | Slash-команды, Autocomplete, кнопки пагинации |
| Gateway Ready / восстановление доступности | Восстановление наблюдения и сверка |

Использовать минимально необходимые Gateway Intents, включая `Guilds` и `GuildVoiceStates`.

`MessageContent` не требуется.

**Важно:** временная недоступность guild во время сбоя Discord не равнозначна удалению бота. При такой недоступности SQLite не очищается.

## 11. Восстановление состояния

После запуска:

1. Открыть заранее подготовленную SQLite без автоматического применения миграций.
2. Подключиться к Discord Gateway.
3. Дождаться загрузки доступных guild и их голосовых состояний.
4. Сверить зарегистрированные триггеры с Discord.
5. Удалить записи физически несуществующих каналов.
6. Удалить пустые временные каналы с оставшимся бюджетом попыток.
7. Сохранить занятые временные каналы.
8. Продолжить обработку событий.

Пользователей, находившихся в триггерах до запуска, не перемещать.

Новые входы, полученные после загрузки начального состояния guild и во время стартовой сверки, обрабатываются после её завершения. Канал создаётся, только если пользователь всё ещё находится в исходном триггере и выполняются остальные условия создания. Начальные голосовые состояния не считаются новыми входами.

При восстановлении соединения выполнять аналогичную сверку после получения достоверного состояния.

Периодический REST-опрос Discord не использовать.

Для операций создания, подсчёта лимитов и удаления предусмотреть защиту от параллельных событий, чтобы два одновременных входа не обходили установленный лимит и не порождали неконсистентные записи.

## 12. Обработка ошибок

- Недостаточные разрешения при регистрации — отказ с указанием недостающих прав.
- Отзыв разрешений во время работы — сохранение триггера, логирование ошибки.
- Ошибка создания — пользователь остаётся в триггере.
- Пользователь вышел до завершения создания — откат.
- Ошибка перемещения — откат.
- Удаление — до трёх автоматических попыток за всё время канала, с сохранением потраченной попытки перед запросом.
- Ошибка явно запущенной миграции SQLite — отказ операции обновления БД; приложение запускается после успешной подготовки БД.
- Ошибка Discord Gateway — восстановление соединения средствами discord.js.
- Неудачный деплой — статус failed в GitHub Actions без автоматического отката.

Операции удаления и очистки записей должны быть идемпотентными.

REST-запросы должны выполняться только для необходимых операций; использовать встроенную обработку rate limits discord.js.

## 13. Логирование

Логи в формате JSON через stdout.

Логировать:

- Подключение и отключение Discord Gateway.
- Успешные создания и удаления временных каналов.
- Административные операции.
- Изменения лимитов.
- Передачу и назначение владельца.
- Ошибки Discord API и SQLite.
- Результаты развёртывания и восстановления состояния, относящиеся к работе бота.

Контекст записи: timestamp, event, guild ID, channel ID, trigger ID, user ID, результат операции, причина ошибки при наличии.

Секреты, код-фразы, Discord Token не логировать. Исключение — первоначальная генерация кода при запуске без владельца, когда его необходимо показать оператору через Docker-логи. Восстановительный код выводится только в stdout CLI-команды.

Docker logging driver: `json-file`.

Параметры:

- `max-size: 10m`
- `max-file: 3`

Никакого отдельного постоянного хранилища истории логов.

## 14. Docker

Docker-образ должен поддерживать:

- `linux/amd64`
- `linux/arm64`

Использовать multi-stage Dockerfile. В рабочий образ помещать только необходимые runtime-зависимости, скомпилированное приложение и подготовленные миграции.

Состав финального образа минимизируется: Node.js, dist основного процесса и операторского CLI, скомпилированные миграции, production-зависимости, необходимые нативные библиотеки и метаданные запуска. Исходники TypeScript, тесты, coverage, инструменты TypeScript/Vitest/ESLint/Prettier и компиляции нативных модулей, документация разработки, кэши и настройки редактора остаются за пределами финального образа. Сборка и установка зависимостей выполняются на промежуточных этапах; запуск приложения и миграций не требует сборки или установки пакетов.

Контекст сборки ограничивается через .dockerignore: локальные node_modules, .git, секреты .env, локальные БД, логи и артефакты разработки не передаются в сборку. При приёмке проверяется фактический состав финального образа и работоспособность приложения, операторского CLI и миграций с оставленными runtime-зависимостями.

Нативный `better-sqlite3` собирается под соответствующую архитектуру.

SQLite хранится в постоянном Docker Volume.

Конфигурация на сервере:

```text
/opt/discord-voice-bot/
├── docker-compose.yml
├── .env
└── .deploy.env
```

`.env` содержит runtime-секреты. `.deploy.env` содержит используемый Docker image tag.

Контейнер запускается с `restart: unless-stopped`.

### Docker Healthcheck

Без HTTP-сервера и открытых сетевых портов.

Бот считается готовым после инициализации SQLite и подключения к Discord Gateway.

Healthcheck должен отличать готовый процесс от зависшего или завершившегося процесса, используя локальный механизм проверки состояния.

## 15. GitHub и CI/CD

### Репозиторий

- Название: `temp-voice`.
- Доступ: публичный.
- Лицензия: MIT.
- Ветка `main` защищена.
- Изменения через Pull Request.
- Обязательные успешные проверки CI.
- Одобрение другого разработчика не требуется.

### CI

Проверки выполняются:

- При Pull Request.
- При push в `main`.
- При создании релизного Git-тега.

Проверки:

- `tsc --noEmit`.
- ESLint.
- Vitest.

Неуспешная проверка блокирует релизную публикацию.

### Релизы

Формат Git-тега: `vX.Y.Z`.

Тег должен указывать на коммит из истории `main`.

При создании тега GitHub Actions:

1. Проверяет допустимость релиза.
2. Запускает CI.
3. Собирает multi-arch Docker-образ.
4. Публикует в GHCR теги версии и `latest`.
5. Запускает deployment job на self-hosted runner.

### Развёртывание

Self-hosted GitHub Runner расположен на том же сервере, что и бот.

Он выполняет:

1. Обновление версии образа в `.deploy.env`.
2. `docker compose pull`.
3. `docker compose up -d`.
4. Ожидание `healthy`.
5. Завершение workflow со статусом успеха либо ошибки.

В случае ошибки автоматического отката нет.

До запуска новой версии БД подготавливается отдельной явно запущенной операцией миграции. Порядок применения и отката БД выбирается отдельно от смены версии образа; запуск контейнера не выполняет миграции.

Workflow для непроверенных Pull Request не должен запускаться на self-hosted runner с доступом к Docker-хосту.

## 16. Миграции и данные

Миграции создаются исключительно командой TypeORM migration:generate и хранятся в репозитории. Ручное написание миграции или изменение операций up/down допустимы только по прямому явному запросу пользователя; общее поручение реализовать функциональность таким запросом не является. Подробное обязательное правило находится в [архитектуре проекта](../../project-architecture.md#миграции). В рабочий образ включаются скомпилированные миграции.

Миграции задают версионируемые переходы схемы и необходимые преобразования данных: up переводит БД в состояние новой версии, down восстанавливает совместимость с предыдущей. Оба направления проектируются и проверяются вместе, с приоритетом сохранения данных. Неизбежные потери данных являются отдельным заранее согласуемым компромиссом.

Применение и откат миграций выполняются отдельными явными командами TypeORM CLI по решению оператора или процесса развёртывания. Подключение к БД и запуск приложения не применяют и не откатывают миграции. Момент выполнения и целевая версия относятся к управлению развёртыванием.

При неудачной миграции операция обновления БД завершается ошибкой; запуск новой версии выполняется после успешной подготовки схемы. Откат кода и откат БД — отдельные управляемые операции.

Автоматические резервные копии SQLite не создаются. При необходимости резервное копирование выполняется оператором вручную с использованием согласованного механизма копирования SQLite.

## 18. Тестирование и критерии приёмки

Перед выпуском первой версии должны быть проверены следующие сценарии:

1. Регистрация и снятие наблюдения за триггером.
2. Повторная регистрация активного триггера.
3. Создание канала при новом подключении.
4. Создание канала при перемещении между голосовыми каналами.
5. Игнорирование подключений ботов.
6. Игнорирование уже находящихся в триггере пользователей при запуске.
7. Правильное копирование настроек и индивидуальных разрешений.
8. Сохранение прав создателя после выхода.
9. Удаление канала при выходе последнего обычного пользователя.
10. Удаление канала, в котором остались только боты.
11. Сохранение занятых каналов после `/voice unwatch`.
12. Одинаковое поведение при физическом удалении триггера.
13. Подсчёт общих и индивидуальных лимитов.
14. Повторная регистрация триггера с существующими временными каналами.
15. Cooldown 5 секунд.
16. Откат создания при выходе пользователя или ошибке перемещения.
17. Ограничение в три автоматические попытки удаления, включая сохранение потраченной попытки при аварии процесса.
18. Учёт проблемных каналов в лимитах и списках.
19. Инициализация владельца и погашение код-фразы.
20. Передача владения и истечение срока кода.
21. Защита от перебора код-фраз.
22. Разграничение `ManageGuild` и глобального владельца.
23. Корректная работа RU/EN локализации.
24. Пагинация и ограничение времени действия кнопок.
25. Восстановление после перезапуска и переподключения.
26. Отсутствие очистки данных при временной недоступности guild.
27. Миграции на существующей SQLite.
28. Работа multi-arch Docker-образа.
29. Успешный и неуспешный сценарии CI/CD.
30. Сохранность данных при пересоздании контейнера.

Тесты бизнес-логики должны работать без реального подключения к Discord, с подменой внешних зависимостей.
