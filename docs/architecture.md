# Общие архитектурные правила

Этот документ определяет ответственность компонентов и правила их взаимодействия. Конкретный состав приложения, стек, интеграции и эксплуатационные решения описываются в [архитектуре проекта](project-architecture.md). Правила работы с кодом находятся в [AGENTS.md](../AGENTS.md).

## Основные принципы

Архитектура строится вокруг функциональных областей, их данных и сценариев. Каждая ответственность имеет явного владельца.

Состав компонентов выбирается по текущим требованиям. Паттерны и принципы проектирования используются для упрощения кода. Отдельный слой, интерфейс или модель должны иметь самостоятельную ответственность.

Архитектура проекта различает реализованное состояние, согласованное целевое устройство и предложения. Для существующего приложения переход к целевому устройству выполняется проверяемыми этапами с учётом совместимости и сохранности данных.

## Модули и владение

Код группируется по функциональным модулям, внутри которых компоненты разделяются по ролям. Модуль владеет своими правилами, состоянием и операциями.

Публичный контракт модуля включает только необходимые другим частям приложения возможности. Межмодульное взаимодействие использует этот контракт. Внутренние репозитории и детали хранения остаются у владельца данных.

Общая техническая часть содержит определения, независимые от предметной области. Она не зависит от функциональных модулей.

Циклическая зависимость требует пересмотра ответственности и направления взаимодействия. Порядок создания объектов сам по себе не устраняет архитектурный цикл.

## Роли компонентов

| Роль | Ответственность |
| --- | --- |
| Controller / Observer | Принимать внешний вход, разбирать транспортные данные, вызывать операцию и преобразовывать результат в ответ. Группировать методы по функциональной ответственности. |
| Worker | Получать фоновое задание или событие, управлять техническим выполнением и вызывать операции приложения. |
| Handler | Координировать конкретный сценарий: подготовить вход, вызвать необходимые бизнес-возможности в установленном порядке и сформировать результат. |
| Service | Содержать бизнес-правила своей области, проверять допустимость операций и определять переходы состояния. |
| Repository | Инкапсулировать запросы, преобразование сохраняемых данных и атомарные операции хранилища. |
| Storage | При необходимости управлять политикой кэширования и технической координацией доступа к данным, используя репозитории и инфраструктурные контракты. |
| Adapter | Скрывать протокол, клиент, форматы и специфичные ошибки внешней системы за операциями, необходимыми приложению. |
| Module / composition root | Создавать и связывать компоненты, выбирать реализации зависимостей и организовывать жизненный цикл. |

Для простого вызова отдельный Handler не требуется. Worker, Controller или Observer может вызвать Service напрямую, если самостоятельной координации нет.

Общие бизнес-сценарии используются разными входами приложения. Их правила не дублируются в транспортных, фоновых и административных обработчиках.

## Направление зависимостей

Типовой поток выполнения:

```text
Внешний вход → Controller / Observer → Handler → Service
Фоновый вход → Worker ────────────────────────→ Service
                                                 ├→ Repository
                                                 └→ Adapter

При необходимости кэширования: Service → Storage → Repository
```

Схема описывает роли и допустимые зависимости; конкретный состав определяется сценарием.

- Транспортные компоненты работают с операциями приложения; они не выполняют запросы к хранилищу.
- Handler координирует возможности Service и не обходит их бизнес-правила прямым изменением данных.
- Service получает данные и результаты операций через контракты. Он не управляет транспортными объектами, запросами, клиентами хранилищ, ключами кэша или объектами транзакций.
- Repository отвечает за хранение данных и не зависит от вызывающих Handler, Service или внешнего транспорта.
- Storage отвечает за политику доступа к данным; решения о бизнес-допустимости остаются в Service.
- Adapter скрывает внешний механизм и не становится владельцем бизнес-правил.
- Сборка зависимостей и управление техническими ресурсами находятся в точках сборки приложения.

Интерфейс вводится, когда он образует полезную границу, изолирует внешний механизм или позволяет подменить зависимость. Подходящий публичный контракт зависимости переиспользуется.

## Модели и бизнес-правила

Простая детерминированная логика может находиться в функции или модели. Набор правил выделяется в отдельный компонент, когда это даёт ясную ответственность и устраняет повторение.

Доменная сущность создаётся при наличии идентичности, поведения или инвариантов. Модель хранения описывает сохраняемые данные. Соответствие между ними выбирается по задаче; наличие записи в хранилище не требует отдельной доменной модели.

Объект значения нужен для самостоятельных правил допустимости, нормализации или сравнения. Типы и модели должны отражать допустимое состояние.

Правило определяется у владельца и применяется во всех сценариях, которым оно необходимо.

## Проверка входа и доступа

Проверки разделяются по смыслу:

- транспортный слой разбирает формат входа и сведения вызывающей стороны;
- операция проверяет допустимые сочетания параметров и подготавливает внутренние данные;
- бизнес-слой проверяет допустимость действия над актуальным состоянием.

Один и тот же инвариант не дублируется на нескольких слоях. Входные идентификаторы, предварительно отфильтрованные варианты и видимость действия не заменяют проверку доступа.

Право, зависящее от текущего владельца или состояния ресурса, проверяется в соответствующей операции и согласуется с изменением этого состояния.

## Хранение и транзакции

Для каждого вида данных определяются источник истины, владелец и допустимые производные представления. Временное состояние и кэш имеют явные правила потери и восстановления.

Repository инкапсулирует одну связанную область хранения. Он может работать с несколькими тесно связанными записями, если они составляют одну атомарную операцию.

Транзакция нужна, когда частичное сохранение нарушает инвариант. Её граница находится в самом низком компоненте, который видит всю атомарную операцию хранения. Детали транзакции не передаются через бизнес-сервисы и обработчики.

Последовательные вызовы разных репозиториев сами по себе не дают общей атомарности. Операции между независимыми модулями требуют явно спроектированной границы сохранения.

Операция с внешней системой и изменение локального состояния требуют согласованного порядка действий. Если общей транзакции нет, определяются компенсация, повторное выполнение и восстановление после частичного успеха.

## Конкурентность и повторы

Асинхронные операции могут пересекаться даже в одном процессе. Для инварианта определяется область конкуренции, охватывающая все затрагиваемые данные.

Проверка состояния и его изменение должны оставаться согласованными при параллельном выполнении. После ожидания актуальность значимых условий проверяется повторно.

Повторная доставка события, повтор запроса и восстановление после ошибки не должны повторять недопустимый бизнес-эффект. Идемпотентность и ограничения повторов определяются контрактом операции.

Техническая координация располагается на границе выполнения сценария или доступа к данным в соответствии с архитектурой проекта. Бизнес-сервис получает факты и результаты операций, а не объекты блокировок.

Средство координации должно охватывать всех участников конкурентной операции. Защита одного процесса не считается защитой от независимого процесса.

## Внешние системы и восстановление

Контракт адаптера описывает необходимые приложению операции и значимые результаты. Проверяются используемые поля внешнего ответа; внешние данные не принимаются за достоверные только из-за объявленного типа.

Недоступность ресурса, отсутствие в неполном локальном представлении и подтверждённое удаление различаются. Необратимая очистка опирается на достаточные свидетельства.

Восстановление использует те же операции приложения и сохраняет их инварианты. Определяются порядок сверки, взаимодействие с новыми событиями и критерии достоверности состояния.

## Конфигурация и жизненный цикл

Конфигурация загружается, преобразуется и проверяется на границе запуска. Компоненты получают узкие типизированные неизменяемые настройки и не зависят от общего источника окружения.

Значения по умолчанию и правила проверки имеют одного владельца. Разные точки входа используют общие определения, получая только необходимые им зависимости.

Для запуска определяются порядок инициализации и критерии готовности. Для завершения — прекращение приёма новых операций, ожидание или отмена текущих действий и освобождение ресурсов.

Проверка состояния должна соответствовать эксплуатационному контракту: существование процесса, его работоспособность и готовность обслуживать операции могут требовать разных свидетельств.

## Ошибки и наблюдаемость

Ошибки выражают смысл отказа на своей границе. Специфичная ошибка внешней системы преобразуется в понятный контракт там, где это требуется вызывающей стороне. Бизнес-ошибка не определяет формат транспортного ответа.

Логирование содержит достаточный безопасный контекст для диагностики операции и её частичного выполнения. Секреты и чувствительные данные обрабатываются по явно определённым правилам проекта.

Контракт известных ошибок документируется по правилам разработки. Техническая проверка документации не заменяет анализа фактического поведения.

## Архитектурное review

При проверке изменения необходимо установить:

1. Соответствует ли новая логика ответственности компонента и владельцу данных?
2. Сохранены ли направления зависимостей и публичные контракты модулей?
3. Применяются ли общие бизнес-правила во всех входах без дублирования?
4. Правильно ли определены атомарность, конкурентность, повторы и частичный успех?
5. Остаются ли внешние механизмы и конфигурация за установленными границами?
6. Имеет ли каждая новая абстракция практическую ценность для текущей задачи?
7. Для рефакторинга: подтверждено ли сохранение поведения и предусмотрен ли переход данных и контрактов, если он требуется?

Review указывает конкретное нарушение ответственности, контракта или требования. Предпочтение другого дизайна само по себе не является основанием менять согласованный подход.
