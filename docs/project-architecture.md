# Архитектура TempVoice

## Назначение и технические решения

Документ определяет целевую архитектуру TempVoice — мультисерверного Discord-бота для временных голосовых каналов. Требования первой версии находятся в [spec.md](specs/001-initial-project/spec.md). Общие правила разработки находятся в [AGENTS.md](../AGENTS.md), общие архитектурные положения — в [architecture.md](architecture.md).

Утверждённый стек: Node.js LTS, TypeScript strict, NestJS Standalone, Necord поверх discord.js v14, TypeORM, SQLite с better-sqlite3 и Vitest. Конкретные версии и режим модулей фиксируются в plan после проверки совместимости.

Nest application context собирает зависимости и управляет жизненным циклом приложения. Necord связывает события и interactions discord.js с методами Observer и Command Controller через декораторы и подключает guards, pipes, interceptors и filters Nest. TypeORM управляет ORM-моделями, запросами и миграциями SQLite.

## Границы первой версии

- Один постоянно работающий процесс бота, несколько guild, одна SQLite на постоянном Docker Volume.
- Отдельная CLI-точка входа для операторских операций с SQLite.
- Discord Gateway доставляет события и interactions.
- Постоянное состояние хранится в SQLite, текущее состояние каналов и участников предоставляется Discord.

## Поток выполнения и роли

```text
Discord Gateway / interaction
            ↓
Discord Observer / Command Controller
            ↓
Handler, если сценарию нужна координация
            ↓
Service ─────────→ Repository → SQLite
   └─────────────→ узкий Discord-адаптер → discord.js

Сверка состояния / CLI → те же Handler и Service
```

| Роль | Ответственность |
| --- | --- |
| Observer / Command Controller | Сгруппировать обработчики событий или команд по функциональной ответственности. Методы с декораторами Necord получают Discord-вход, разбирают параметры, вызывают операцию и преобразуют результат в ответ. Управляют reply/defer, ephemeral и форматом компонентов. |
| Service | Проверить допустимость операции, применить лимиты, cooldown, правила владения и переходов состояния своей области. |
| Repository | Выполнить SQL/ORM-запросы, подсчёты, условные записи и атомарные операции SQLite. |
| Discord-адаптер | Скрыть Client, Gateway cache, REST, permissions overwrites и ошибки Discord за операциями, нужными сценарию. |
| App / composition root | Собрать Nest application context и координировать запуск и завершение через lifecycle hooks. |

Узкие контракты Discord-операций определяются у потребляющей функциональной области; адаптеры скрывают `Client` и `Interaction` discord.js. Объекты запросов и транзакций TypeORM остаются внутри Repository.

Готовые enum и типы discord.js переиспользуются, если подходят по смыслу. Собственные контракты описывают необходимые сценарию данные и внешние действия.

## Логические модули и владение данными

| Модуль | Ответственность и данные |
| --- | --- |
| `App` | Сборка зависимостей, запуск, завершение, координация готовности компонентов. |
| `Discord` | Client, listeners, slash definitions и их синхронизация, `/voice`, `/owner`, Autocomplete, RU/EN ответы, пагинация, адаптеры Discord API. |
| `Triggers` | Регистрация, снятие наблюдения, реакция на AFK и физическое удаление триггера; `voice_triggers`. |
| `Voice` | Жизненный цикл временного канала и Handler сценариев, объединяющих Voice, Triggers и Limits; `temporary_channels`, отметки незавершённой очистки `pending_guild_removals`. |
| `Limits` | Общий лимит guild, применение общего и индивидуального ограничений, cooldown; `guild_settings` и cooldown в памяти. Индивидуальный лимит хранится у Triggers. |
| `Ownership` | Назначение, передача, восстановление владельца, защита claim; `bot_owner`, `owner_codes`, `claim_attempts`. |
| `Reconciliation` | Сверка после запуска и восстановления достоверного состояния Discord через операции Triggers и Voice. |
| `Infrastructure/Database` | Подключение SQLite, настройка драйвера, применение миграций и закрытие соединения. |
| `Logging` | Общий структурированный JSON-вывод с безопасным контекстом. |
| `Health` | Локальная готовность и актуальность состояния процесса без HTTP. |
| `Cli` | Разбор операторской команды и вызов Ownership. |
| `Core` | Только действительно общие технические компоненты без зависимости от функциональных областей. |

Команды guild и владельца группируются внутри Discord.

Repository и ORM-модели располагаются у владельца данных. Database регистрирует модели в TypeORM DataSource. Команды вызывают Handler или Service, а межмодульные операции используют публичные методы владельца данных.

Handler в Voice получает количества временных каналов через VoiceService и индивидуальную настройку через TriggersService, затем передаёт эти факты LimitsService. Triggers и Limits не импортируют Voice. Общие сценарии регистрации, изменения лимитов и очистки guild используют публичные операции владельцев данных.

Внутри Discord разделяются два модуля сборки. DiscordGatewayModule регистрирует Necord и адаптеры внешних операций; он не импортирует бизнес-сервисы. DiscordModule регистрирует входные Observer и Controller и использует Handler Voice и Ownership. Такое направление исключает обратный импорт транспорта из бизнес-модулей.

Реализованные бизнес-компоненты Voice собираются через `VoiceModule.withGateway(...)`: переданный модуль должен экспортировать `VoiceChannelGatewayToken` с реализацией контракта Voice. `ReconciliationModule.withGateway(...)` подключает ту же сборку сценариев. DiscordModule передаёт DiscordGatewayModule; бизнес-модули не импортируют конкретный транспорт. TriggersModule и LimitsModule экспортируют свои Service; Repository остаются у владельцев. Основной App подключает DiscordModule, миграции и восстановление незавершённой очистки выполняются до Gateway login.

## Источники состояния

| Источник | Что в нём хранится |
| --- | --- |
| SQLite | Регистрации триггеров, лимиты, идентичность временных каналов, создатели, потраченные попытки удаления, владелец, хеши кодов, попытки и блокировки claim. |
| Discord | Фактическое существование каналов, категории, настройки, разрешения, участники и их голосовые состояния. |
| Память процесса | Cooldown `(guild_id, user_id)`, сессии пагинации, текущие операции, локальная сериализация и готовность. |

Discord ID хранятся строками. Имя канала не является идентификатором и не сохраняется в SQLite. Текущие настройки триггера берутся из достоверного состояния Discord перед созданием.

SQLite определяет, какими каналами управляет бот. Отсутствие канала в неполном cache, временная недоступность guild и ошибка доступа не доказывают физическое удаление. Сверка удаляет записи только при подтверждённом отсутствии ресурса.

`unwatch` сохраняет индивидуальный лимит; физическое удаление триггера убирает его лимит. В обоих случаях существующие временные каналы продолжают учитываться и управляться. Каскадное удаление временных каналов вместе с триггером запрещено.

Индивидуальный лимит можно задать до watch для подходящего голосового канала. Такая конфигурация остаётся неактивной до отдельной регистрации триггера.

## Конкурентные события

Один Node.js-процесс не устраняет конкуренцию между асинхронными обработчиками. Проверка лимита, создание, запись и перемещение должны образовывать одну согласованную application operation.

Для plan предлагается последовательное выполнение изменяющих операций внутри одного guild. Разные guild могут обрабатываться независимо. В ту же границу должны входить создание, удаление, изменение лимитов и триггеров, очистка guild и сверка. Отдельная блокировка только на пользователя или триггер не защищает общий лимит guild.

Координатор операций guild вызывается на границе сценария. Вложенный вызов в уже занятой очереди не должен ожидать повторного захвата той же очереди. Порядок зависимостей фиксируется в plan.

После ожидания нужно повторно проверить актуальное состояние: активность триггера, лимиты, cooldown и нахождение пользователя в исходном канале. При событии без смены `channel_id` повторное создание не запускается. Уже находившиеся в триггере пользователи не превращаются в новые входы при старте или сверке.

VoiceEntryService записывает переход при получении события до очереди и хранит последовательный номер пользователя, поколение snapshot и границу успешного watch. Создание один раз закрепляет текущий переход; повторная доставка не становится новым входом после истечения cooldown. Уход и возврат в тот же канал меняют идентичность входа. Reconciliation начинает новое поколение после восстановления достоверности guild; старые входы теряют актуальность. Новые входы и выходы во время сверки сохраняются до её окончания.

Observer обрабатывает уведомления SDK вне контекста текущей операции координатора. Это необходимо и для синтетического `channelDelete`, который discord.js вызывает из собственного REST-метода удаления: уведомление становится отдельной ожидающей операцией. Внутренний повторный захват очереди сценарием по-прежнему запрещён.

Удаление и `channelDelete` идемпотентны. Одновременные запросы на удаление одного канала не порождают независимые попытки. `delete_attempts` увеличивается в SQLite перед запросом к Discord; незавершённая при аварии попытка остаётся потраченной. После исчерпания трёх попыток новые автоматические запросы удаления не запускаются. Подтверждённое отсутствие канала позволяет убрать запись независимо от счётчика.

DeleteTemporaryChannelHandler объединяет выполняющиеся и ожидающие запросы по guild/channel. Откат использует внутреннюю операцию без повторного захвата очереди; уже ожидающий запрос получает результат той же попытки. Неизвестный состав и подтверждённая занятость до начала попытки не тратят бюджет. После резервирования пустота проверяется ещё раз: изменение состава предотвращает DELETE, но потраченная попытка не возвращается. Необратимый отказ БД закрывает допуск новых операций координатора и сообщает основному процессу о необходимости завершения. BeforeApplicationShutdown ожидает текущие операции до 15 секунд перед закрытием Discord и SQLite; health-файл ещё не реализован.

CLI восстановления владельца потенциально работает вторым короткоживущим процессом. Очередь в памяти бота его не защищает. Claim, transfer и recovery должны согласовываться атомарными операциями SQLite и повторной проверкой актуального владельца, а не сохранённой в памяти авторизацией.

## Транзакции и внешние действия

Repository скрывает TypeORM и конкретную SQLite-транзакцию.

Проверка и погашение кода вместе с назначением владельца являются одной атомарной persistence-операцией Ownership. Его Repository работает с соответствующими системными таблицами в одной SQLite-транзакции.

Проверка кода, актуальности владельца и срока действия согласуется с условной записью. Границы межмодульных атомарных операций определяются в plan.

Discord REST и SQLite не образуют общую транзакцию. SQL-транзакцию нельзя держать открытой во время ожидания Discord API. Для создания используется порядок из spec: проверить → создать Discord-канал → сохранить ID → повторно проверить положение пользователя → переместить → установить cooldown после успеха.

При уходе пользователя или ошибке перемещения выполняется компенсационное удаление через общий механизм Voice. Если в канале уже есть другие обычные пользователи, он сохраняется до опустения. Если удаление не удалось, запись остаётся в SQLite, учитывается в лимитах и сохраняет число потраченных попыток. Неудавшаяся запись в SQLite после Discord create требует попытки удалить уже известный канал и регистрации безопасного диагностического контекста. Нельзя сообщать об успешном создании без сохранённой записи.

Согласованное ограничение первой версии: аварийное завершение между Discord create и сохранением ID может оставить канал вне SQLite. Автоматическое обнаружение такого канала не гарантируется; оператор удаляет его вручную. По имени искать и удалять предположительно принадлежащие боту каналы нельзя. Точное представление ошибок частичного выполнения закрепляется в plan.

## Запуск, восстановление и завершение

Порядок запуска: загрузить и проверить конфигурацию → открыть SQLite → применить миграции → подготовить зависимости и обработчики → подключить Discord → получить достоверное состояние доступных guild → выполнить сверку → перейти к штатной обработке.

Ошибка миграции останавливает запуск. Начальный голосовой snapshot не запускает создание каналов. Новые входы после получения начального состояния guild сохраняются на время сверки и обрабатываются после неё с повторной проверкой актуального положения пользователя.

Сверка сравнивает зарегистрированные ID, снимает недействующие триггеры, очищает подтверждённо отсутствующие каналы и вызывает обычное удаление пустых каналов с оставшимся бюджетом попыток. Занятые каналы сохраняются. Боты не учитываются при определении пустоты.

После восстановления Gateway или доступности guild применяется тот же сценарий. Периодического REST-опроса нет. Используются Gateway cache и необходимые адресные обращения; обработка rate limits остаётся за discord.js. Временная недоступность не вызывает очистку SQLite.

При завершении прекращается приём новых операций, завершаются либо отменяются текущие сценарии в согласованном порядке, закрываются Discord-клиент и SQLite, сбрасывается готовность. Конкретные таймауты shutdown определяются в plan вместе с Docker.

## Команды, доступ и владение

Discord-модуль описывает команды, локализации, контексты использования и начальные permissions через Necord. Guards проверяют доступ на транспортной границе; проверки актуального владения и допустимости операции выполняются также в соответствующем сценарии. Серверная логика повторно проверяет контекст, пользователя и введённые ID. Autocomplete и видимость команды не являются авторизацией. `/voice` требует `ManageGuild` в guild; `/owner`, кроме claim, требует актуального владельца и DM.

Команды владельца должны быть зарегистрированы с подходящим глобальным scope и DM-контекстом. Доступность проверяется реальным interaction в DM; guild-only регистрация для них недостаточна. См. [контексты команд Discord](https://docs.discord.com/developers/interactions/application-commands#contexts).

Правила назначения владельца, одноразовости кода и передачи принадлежат Ownership, а не Discord-команде. После блокировки на 15 минут доступны новые пять попыток; успешный claim сбрасывает счётчик и блокировку этого пользователя. Проверка хеша безопасна, открытые коды в БД не сохраняются.

Проверка актуального владельца выполняется при допуске операции к исполнению после ожидания в очереди. Уже допущенная команда может завершиться после передачи или восстановления владения. Следующие команды и действия проверяют новое состояние.

Пагинация принадлежит Discord-представлению: только вызвавший пользователь, 15 минут, память процесса. Проверки доступа также действуют для Autocomplete и кнопок. После перезапуска сессии не восстанавливаются.

## Конфигурация, логи и healthcheck

Приложение и CLI получают конфигурацию через соответствующие Nest application context. Настройки Discord-клиента и SQLite передаются их компонентам через DI.

Для runtime-настроек и CLI используются общие правила без обязательного запуска Discord-клиента. Ключи окружения, значения по умолчанию и механизм загрузки фиксируются в plan; секреты не выводятся в ошибках конфигурации.

### Env и модульные Config

Принят подход конфигурации из GoldGiverBackend: env-группы → валидация → ConfigFactory → Config → потребитель через DI.

- Env-слой находится в `src/config/env`. Классы `Variables/*EnvVariables.ts` задают свойства с `Expose`, преобразование через class-transformer, дефолты и проверки class-validator. Общий `ValidateEnvGroup` проверяет одну группу; `ValidateEnv` проверяет группы из `EnvVariableGroupsConst` и объединяет результат. `EnvironmentVariablesType` описывает пересечение типов групп. Сообщения об ошибках содержат только имена настроек, без значений и target.
- `ConfigModule.forRoot` загружает `.env` и проверяет окружение в composition root. Основной процесс проверяет Discord, Database и Health; CLI проверяет только Database. Нормализация относительных путей выполняется в env-слое. Дефолты и проверки не повторяются в ConfigFactory или потребителях.
- Каждый модульный `*Config` находится у владельца, например `Discord/Config/DiscordConfig.ts`. Он хранит значения в private readonly полях и предоставляет getters; не читает окружение и не зависит от Nest. Общий env-объект не подменяет узкие Config.
- `Config/Factory/*ConfigFactory.ts` — injectable-класс с `create(): Config`, реализующий `FactoryInterface<Config>`. Он получает `ConfigService<СвояГруппаEnv, true>` и читает готовые значения с `{ infer: true }`. Производный Config может собираться из других внедрённых Config без повторного чтения env.
- `Core/Provider/CreateConfigProvider.ts` регистрирует результат фабрики под токеном класса Config. Общий `FactoryInterface` находится в `Core/Interface`. Регистрация выполняется в scope потребителя, Config экспортируется только при наличии внешнего потребителя. Отдельные `*ConfigurationModule` и сервис-обёртка над ConfigService не создаются. В текущем каркасе App регистрирует конфиги Discord и Health; при подключении их функциональных потребителей регистрация переходит в соответствующий scope.
- Options-фабрика стороннего модуля получает готовый Config через DI и реализует публичный options-factory интерфейс зависимости. `App/Factory/DatabaseOptionsFactory.ts` реализует `TypeOrmOptionsFactory` и собирает параметры SQLite с принадлежащим composition root списком моделей и миграций. `DatabaseConfigFactory` и `CreateConfigProvider(DatabaseConfig, DatabaseConfigFactory)` регистрируются в `extraProviders` TypeORM; технический Database не импортирует App.
- Основной процесс и операторские команды используют Nest Standalone. TypeORM CLI получает options той же фабрики через краткий контекст `CliModule`, который проверяет только Database и закрывается до передачи DataSource инструменту TypeORM. Для миграций не нужны Discord token, health-настройки или запуск Discord Client. Специальный путь обхода DI из HTTP-проекта сюда не переносится.

Getters, конфигурационные константы и DI wiring не требуют отдельных автоматических тестов. Рефакторинг проверяется статическим анализом, сборкой и локальным запуском соответствующих точек входа; бизнес-тесты сохраняют свои сценарии.

Logging предоставляет один согласованный JSON-вывод в stdout. Контекст содержит event и применимые Discord ID, результат и безопасную причину ошибки. Не передавать в логгер сырые interactions, аргументы claim, токен или весь объект сторонней ошибки. Исключение для открытого кода в логах — первоначальная генерация при запуске без владельца.

Health не открывает порт. Основной процесс обновляет временный файл после проверки SQLite и готовности Gateway; CLI проверяет его содержимое, живой PID и свежесть. Начальная сверка входит в критерий готовности. Интервалы и shutdown определены в plan; heartbeat не выполняет REST-опрос Discord.

Восстановительный код после успешного изменения SQLite выводится в stdout CLI-команды. Для восстановления запускается отдельный Nest application context с Database и Ownership; Discord-клиент не подключается.

## Кодстайл и проверки

Для нетривиальных изменений используется Spec Kit. Документы активной feature находятся в `docs/specs/001-initial-project/`.

Применение общих правил к TypeScript:

- Корневые точки входа `main.ts`, `bootstrap.ts`, `console.ts` сохраняют эти имена.
- Корневая точка входа `DatabaseDataSource.ts` экспортирует DataSource для TypeORM CLI; состав моделей и миграций задаёт `App/Factory/DatabaseOptionsFactory.ts`.
- Инструментальные конфигурации используют принятые имена, включая `eslint.config.mjs` и `vitest.config.ts`.
- Тесты именуются по основной сущности с суффиксом `.spec.ts`, например `TriggerService.spec.ts`. Генерируемые миграции сохраняют имена генератора TypeORM.
- Обычные импорты находятся сверху, `import type` — отдельным блоком снизу, между блоками пустая строка. В каждом блоке внешние импорты предшествуют проектным, включая относительные пути и alias `src/*`; дополнительные пустые строки между подгруппами не нужны.
- Inline type-спецификаторы запрещены. Классы, необходимые Nest для DI и decorator metadata, импортируются как runtime-значения. Side-effect импорты находятся в начале обычного блока и сохраняют необходимый порядок.
- Все тела `if`, `else`, `for`, `while` и `do...while` заключаются в фигурные скобки.
- Строковые env-ключи допускаются в env-слое и при чтении через типизированный ConfigService в ConfigFactory; отдельные enum, дублирующие свойства env-групп, не создаются. Остальной код получает готовые настройки и не читает `process.env`.
- Форматируемые строки собираются через `sprintf-js` с именованным шаблоном. Интерполяция template literals и конкатенация для этого не используются. Повторяемые шаблоны хранятся в отдельном enum, специфичные для класса — в его `private static readonly` константах.

ESLint использует `eslint.config.mjs`; форматирование Prettier задаётся в `.prettierrc`. Сортировкой импортов управляет `simple-import-sort/imports`, отдельные type-only импорты проверяются правилами `typescript-eslint`, блоки управления — правилом `curly: ["error", "all"]`. Команда форматирования должна применять автоисправления ESLint и завершающий проход Prettier.

Применяется ESLint 10; версии плагинов закреплены в package.json и lockfile. Для `eslint-plugin-explicit-exceptions` 0.13.3 задан адресный npm override на корневой ESLint: объявленный peer range устарел, фактическая совместимость проверена на примерах. После изменения этого набора повторяется проверка диагностик и автоисправлений. Globals Vitest включены только для `*.spec.ts`.

Известные ошибки документируются через JSDoc: `@throws {ТипОшибки}` для синхронного throw и `@throws {Promise<ТипОшибки>}` для отклонения Promise, в том числе у async-метода. Это соглашение `eslint-plugin-explicit-exceptions`; причиной отклонения остаётся сама ошибка. Типы, нужные только документации, импортируются через `import type`. Ссылки из автоисправления оформляются коротким именем или относительным путём.

Проверку выполняют `eslint-plugin-explicit-exceptions` и правила `jsdoc/require-throws-type`, `jsdoc/no-undefined-types` из `eslint-plugin-jsdoc`. Type-aware анализ использует `projectService` и исключает тесты `*.spec.ts` из проверки контракта ошибок.

Бизнес-тесты выполняются через Vitest с подменой Discord-операций. Они защищают лимиты при одновременных входах, cooldown, откат, сохранение занятых каналов и каналов после unwatch, бюджет попыток удаления, однократный claim и блокировки.

Для конкурирующих claim и recovery при необходимости используется реальная SQLite. Discord permissions, копирование настроек, DM-команды, Gateway recovery, multi-arch сборка и сохранность Docker Volume проверяются на тестовой инфраструктуре по критериям приёмки spec.

Команды lint, lint:fix, format, format:check, typecheck, build и запуск Vitest настроены; type-aware правила используют корневой tsconfig.json.
